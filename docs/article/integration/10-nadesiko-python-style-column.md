# コラム: なでしこ3 を Python 風に書く

[第 9 章](09-japanese-implementation-column.md)では、なでしこ3 を基準に置き、他の 17 言語をなでしこ3 に近づけました。
本章は向きを逆にします。**なでしこ3 を Python に近づけて書き**、FizzBuzz とボウリングゲームを Python と TDD で並べながら育てます。

下敷きにしたのは、天清会の note 記事
「[メモ：Python風に書ける「なでしこ3」の資料を整備、notebookLMに追加しました](https://note.com/alive_beetle8120/n/nb1fc5e640795)」
と、その記事で配布されている「なでしこ3をPython風に書くマニュアル」です。
このマニュアルは、なでしこ3 の公式文法にある **行末のコロンとインデントでブロックを表す書き方**（Python 風インラインインデント構文）に記法を統一し、
Python へ移行したときに制御構造の形が変わらないことを狙っています。

マニュアルはブラウザ版（`wnako` v3.7.24）で検証されています。
本章のコードは、本シリーズの処理系である Go 版の `gonako` v3.8.8 で改めて実行し、テストが通ることを確認しました。
あわせて、公式の JavaScript 版 `cnako3` v3.8.7 でも同じテストが通ることを確かめています。
コードは `apps/pystyle/nadesiko/` と `apps/pystyle/python/` にあります。

> **注意**: 本章の書き方は、本シリーズの[なでしこ3 編](../nadesiko/index.md)の書き方とは異なります。
> 本編は「ここまで」でブロックを閉じ、助詞で引数を渡す日本語らしい書き方を基本にしています。
> どちらが正しいという話ではなく、なでしこ3 が両方を受け入れることを示すのが本章の目的です。

## 問い

1. なでしこ3 は、どこまで Python と同じ形で書けるか
2. TDD のサイクル（Red → Green → Refactor）を両言語で並べたとき、どこで差が出るか
3. Python 風に書くことで、なでしこ3 の何が得られ、何が失われるか

## Python 風インラインインデント構文の規則

マニュアルが定める規則のうち、本章のコードに関わるものを抜き出します。

| 規則 | なでしこ3（Python 風） | Python |
|------|----------------------|--------|
| ブロックの開始 | 行末に半角の `:` | 行末に `:` |
| ブロックの範囲 | 半角スペース 4 個の字下げ | 字下げ（PEP 8 では 4 個） |
| ブロックの終了 | 字下げを戻す（「ここまで」は使わない） | 字下げを戻す |
| 関数の呼び出し | `表示(式)`・`要素数(リスト)` | `print(式)`・`len(リスト)` |
| 関数の名前 | 末尾に「処理」を付ける（`加算処理`） | 規則なし |
| ローカル変数 | `変数のF面積` のように `F` を付ける | 宣言は不要 |

関数名に「処理」を付けるのは、標準命令との名前の衝突を避けるためです。
ローカル変数の `F` も同じ理由で、公式の AI 向け文法資料が推奨している書き方です。

### 3 つの書き方を並べる

同じ FizzBuzz 変換を、本編の書き方、Python 風の書き方、Python の 3 通りで並べます。

**本編の書き方**（`apps/nadesiko/src/fizzbuzz.nako3`）

```text
●(Nを)FizzBuzz変換
    もし、N % 15 = 0ならば,「FizzBuzz」を戻す
    もし、N % 3 = 0ならば,「Fizz」を戻す
    もし、N % 5 = 0ならば,「Buzz」を戻す
    Nを文字列変換して戻す
ここまで
```

**Python 風の書き方**（`apps/pystyle/nadesiko/src/fizzbuzz.nako3`）

```text
●(Nの)FizzBuzz変換処理とは:
    もし(N % 15 = 0)ならば:
        「FizzBuzz」を戻す
    違えばもし(N % 3 = 0)ならば:
        「Fizz」を戻す
    違えばもし(N % 5 = 0)ならば:
        「Buzz」を戻す
    違えば:
        文字列変換(N)を戻す
```

**Python**（`apps/pystyle/python/src/fizzbuzz.py`）

```python
def FizzBuzz変換処理(N: int) -> str:
    if N % 15 == 0:
        return "FizzBuzz"
    elif N % 3 == 0:
        return "Fizz"
    elif N % 5 == 0:
        return "Buzz"
    else:
        return str(N)
```

Python 風の書き方と Python は、行数も字下げの位置も一致します。
`もし … ならば:` が `if … :`、`違えばもし` が `elif`、`違えば:` が `else:`、`… を戻す` が `return …` に 1 行ずつ対応します。
本編の書き方は、1 行の `もし` で早期リターンを並べ、最後を「〜して戻す」でつなぐため、日本語の文に近くなります。

Python 側の識別子は、対応が一目で分かるように、なでしこ3 と同じ日本語にしています。
マニュアルの対照表も、Python のコードに日本語の変数名を使っています。
Python は日本語の識別子をそのまま受け付けます（[第 9 章](09-japanese-implementation-column.md)の結果）。

## TDD で FizzBuzz を並べる

ここからは、FizzBuzz を TDD で両言語同時に育てます。
各ステップで、テストと実装を Python → なでしこ3 の順に並べます。

### TODO リスト

- [ ] 1 を渡したら文字列 "1" を返す
- [ ] 2 を渡したら文字列 "2" を返す
- [ ] 3 の倍数を渡したら "Fizz" を返す
- [ ] 5 の倍数を渡したら "Buzz" を返す
- [ ] 15 の倍数を渡したら "FizzBuzz" を返す
- [ ] 1 から N までの結果をリストにする
- [ ] 1 から N までの結果を 1 行ずつ表示する

### テストの土台

Python は pytest の `assert` をそのまま使えます。
なでしこ3 にはテストフレームワークがないため、本編と同じく、比較結果を集計する補助関数を用意します。
本編の `検証` を、Python 風の構文で書き直しました。

```text
# テスト補助（Python 風インラインインデント構文）: 検証結果を集計し、失敗があれば最後にエラーで終了する
成功数 = 0
失敗数 = 0

●(名前と実際と期待で)検証処理とは:
    エラー監視:
        ASSERT等(変数型確認(実際),変数型確認(期待))
        ASSERT等(実際,期待)
        表示(「  ok: {名前}」)
        成功数 = 成功数 + 1
    エラーならば:
        表示(「  NG: {名前}: {エラーメッセージ}」)
        失敗数 = 失敗数 + 1

●テスト結果報告処理とは:
    表示(「  {成功数}件成功、{失敗数}件失敗」)
    もし(失敗数 > 0)ならば:
        エラー発生(「{失敗数}件のテストが失敗しました」)
```

`エラー監視:` と `エラーならば:` は、Python の `try:` と `except:` に当たります。
ここでもコロンとインデントの書き方がそのまま使えます。
`ASSERT等(実際,期待)` は、本編の `実際と期待がASSERT等` を関数の形で呼んだものです。
引数は助詞の順（`AとBが`）に並べます。

型を先に比べているのは、なでしこ3 の `ASSERT等` が文字列 `「1」` と数値 `1` を区別しないためです（本編の[第 6 章](../nadesiko/06-task-runner-and-ci-cd.md)を参照）。
Python の `==` は `"1" == 1` を偽にするため、この工夫は要りません。

### ステップ 1: 最初のテスト（Red）

Python のテスト（`test/test_fizzbuzz.py`）:

```python
from src.fizzbuzz import FizzBuzz変換処理


def test_1を渡したら文字列1を返す() -> None:
    assert FizzBuzz変換処理(1) == "1"
```

なでしこ3 のテスト（`test/fizzbuzz_test.nako3`）:

```text
!「./helper.nako3」を取り込む
!「../src/fizzbuzz.nako3」を取り込む

検証処理(「1を渡したら文字列1を返す」,FizzBuzz変換処理(1),「1」)
テスト結果報告処理
```

実装がない状態で実行すると、両方とも失敗します。

```text
# Python（pytest）
E   ModuleNotFoundError: No module named 'src.fizzbuzz'

# なでしこ3（src/fizzbuzz.nako3 を空ファイルで用意した場合）
[実行時エラー]test/fizzbuzz_test.nako3(4行目): 関数ではない値を呼び出そうとしました。
```

なでしこ3 のエラーは `検証処理` の `エラー監視` では捕まりません。
引数の `FizzBuzz変換処理(1)` を評価する時点で失敗し、`検証処理` が呼ばれる前に実行が止まるためです。
Python でもモジュールの読み込みで止まり、テストは 1 件も実行されません。
Red の段階で止まる場所は、どちらの言語でも同じです。

### ステップ 2: 仮実装（Green）

テストを通す最小のコードを書きます。

```python
def FizzBuzz変換処理(N: int) -> str:
    return "1"
```

```text
●(Nの)FizzBuzz変換処理とは:
    「1」を戻す
```

`return "1"` と `「1」を戻す` が 1 行ずつ対応します。
`return` が文頭に来るか、`を戻す` が文末に来るかの違いだけです。

### ステップ 3: 三角測量

2 つ目のテスト「2 を渡したら文字列 "2" を返す」を加えると、仮実装では通らなくなります。
引数を文字列に変換して返す形に一般化します。

```python
def FizzBuzz変換処理(N: int) -> str:
    return str(N)
```

```text
●(Nの)FizzBuzz変換処理とは:
    文字列変換(N)を戻す
```

`str(N)` が `文字列変換(N)` に対応します。
本編では `Nを文字列変換して戻す` と書いていたところです。
関数の形で書くと、命令名を覚えていれば Python と同じ順で読めます。

### ステップ 4〜5: 3 の倍数と 5 の倍数

「3 を渡したら Fizz」「6 を渡したら Fizz」のテストを加えて `if`、続けて「5 を渡したら Buzz」「10 を渡したら Buzz」で `elif` を加えます。

```python
def FizzBuzz変換処理(N: int) -> str:
    if N % 3 == 0:
        return "Fizz"
    elif N % 5 == 0:
        return "Buzz"
    else:
        return str(N)
```

```text
●(Nの)FizzBuzz変換処理とは:
    もし(N % 3 = 0)ならば:
        「Fizz」を戻す
    違えばもし(N % 5 = 0)ならば:
        「Buzz」を戻す
    違えば:
        文字列変換(N)を戻す
```

比較演算子だけが違います。
Python の等価比較は `==` ですが、なでしこ3 は代入と比較のどちらにも `=` を使います。
マニュアルも、比較に `=`（または全角の `＝`）を使う書き方を採っています。

### ステップ 6: 15 の倍数（条件の順序）

「15 を渡したら FizzBuzz」のテストを加えると、どちらも失敗します。

```text
# Python
E   AssertionError: assert 'Fizz' == 'FizzBuzz'

# なでしこ3
  NG: 15を渡したらFizzBuzzを返す: ASSERT失敗: 『Fizz』と『FizzBuzz』が一致しません。
```

15 は 3 の倍数でもあるため、先頭の `N % 3` の分岐に入ってしまいます。
`if` / `elif` の連鎖は上から順に評価され、最初に成立した分岐だけが実行されます。
この性質は Python と同じです。
15 の倍数の判定を先頭に移すと、冒頭で示した完成形になり、テストが通ります。

### ステップ 7: 1 から N までのリスト（範囲の終了値）

「15 まで作ると 15 件になる」と「15 まで作ったリストの並び」のテストを加えます。

```python
def test_15まで作ると15件になる() -> None:
    assert len(FizzBuzzリスト作成処理(15)) == 15


def test_15まで作ったリストの並び() -> None:
    assert (
        ",".join(FizzBuzzリスト作成処理(15))
        == "1,2,Fizz,4,Buzz,Fizz,7,8,Fizz,Buzz,11,Fizz,13,14,FizzBuzz"
    )
```

```text
検証処理(「15まで作ると15件になる」,要素数(FizzBuzzリスト作成処理(15)),15)
検証処理(「15まで作ったリストの並び」,配列結合(FizzBuzzリスト作成処理(15),「,」),「1,2,Fizz,4,Buzz,Fizz,7,8,Fizz,Buzz,11,Fizz,13,14,FizzBuzz」)
```

`len(…)` が `要素数(…)`、`",".join(…)` が `配列結合(…,「,」)` に対応します。
`配列結合` は助詞が `AをSで` なので、関数の形ではリストが先、区切り文字が後になります。
Python の `join` は区切り文字のメソッドなので、並びが逆になる点に注意します。

実装はどちらも、空のリストに 1 件ずつ追加する形で書きます。

```python
def FizzBuzzリスト作成処理(N: int) -> list[str]:
    結果 = []
    for 番号 in range(1, N + 1):
        結果.append(FizzBuzz変換処理(番号))
    return 結果
```

```text
●(Nまでの)FizzBuzzリスト作成処理とは:
    変数のF結果 = []
    番号を1からNまで繰り返す:
        配列追加(F結果,FizzBuzz変換処理(番号))
    F結果を戻す
```

ここに、マニュアルが「最大の違い」と呼ぶ差があります。
**なでしこ3 の `1からNまで` は N を含み、Python の `range(1, N)` は N を含みません。**
Python で `range(1, N)` と書いたり、なでしこ3 で Python に合わせて `1から(N - 1)まで` と書いたりすると、件数のテストで気づけます。

```text
# Python で range(1, N) と書いた場合
E   AssertionError: assert 14 == 15

# なでしこ3 で 1から(N - 1)まで と書いた場合
  NG: 15まで作ると15件になる: ASSERT失敗: 『14』と『15』が一致しません。
```

「件数」を確かめるテストは、両言語を行き来するときの境界値の誤りを捕まえる安全網になります。

Python ならリスト内包表記で `[FizzBuzz変換処理(数) for 数 in range(1, N + 1)]` と 1 行で書くのが自然ですが、
なでしこ3 には対応する構文がないため、ここでは両言語とも `for` と `append` の形にそろえています。

### ステップ 8: 1 行ずつ表示する（受け入れテスト）

最後に、1 から 15 までを 1 行ずつ表示する処理を加えます。

```python
def FizzBuzz表示処理(N: int) -> None:
    for 値 in FizzBuzzリスト作成処理(N):
        print(値)
```

```text
●(Nまでの)FizzBuzz表示処理とは:
    値でFizzBuzzリスト作成処理(N)を反復:
        値を表示
```

`for 値 in リスト:` が `値でリストを反復:` に対応します。
語順は日本語のままですが、ループ変数・対象・コロンの 3 つの要素はそろっています。

表示の確認は、Python では pytest の `capsys` で標準出力を取り込み、なでしこ3 では `gonako doctest` で表示結果を照合します。

```python
def test_15まで表示する(capsys: pytest.CaptureFixture[str]) -> None:
    FizzBuzz表示処理(15)
    assert capsys.readouterr().out.splitlines() == FizzBuzzリスト作成処理(15)
```

```text
{{{#nako3
!「../src/fizzbuzz.nako3」を取り込む
FizzBuzz表示処理(15)
### 表示結果: 1
### 2
### Fizz
（中略）
### 14
### FizzBuzz
}}}
```

これで TODO リストはすべて完了です。
FizzBuzz のテストは、Python が 10 件、なでしこ3 が 9 件と doctest 1 件です
（Python は表示の確認を pytest の中で行うため 1 件多くなります）。

### 整形ツールが Python に近づける

マニュアルのコードは、括弧と比較を全角で `もし（点数>=60）ならば:` のように書いています。
同じコードを `gonako format` にかけると、括弧と `＝` が半角になり、演算子の前後に空白が入ります。

```text
# 整形前（マニュアルの表記）
●（Nの）FizzBuzz変換処理とは:
    もし（N%15＝0）ならば:

# gonako format の結果
●(Nの)FizzBuzz変換処理とは:
    もし(N % 15 = 0)ならば:
```

本章のコードは、本編と同じく `make format-check`（`gonako format` との差分がないこと）を CI で検査しているため、整形後の半角の表記で載せています。
結果として、Python の `ruff format` を通したコードと見た目がさらに近くなりました。

## TDD でボウリングゲームを並べる

FizzBuzz は、1 つの数を受け取って 1 つの文字列を返すだけで、状態を持ちません。
ボウリングゲームは、前の投球が後の得点に影響します。
ループの中で投球の位置を進める手続きと、投球を貯めていくオブジェクトの両方が出てくるため、
Python のクラスをなでしこ3 でどう書くかも比べられます。

題材は、演習リポジトリ [k2works/from-objects-to-functions-excersice](https://github.com/k2works/from-objects-to-functions-excersice) のなでしこ3 版サンプルにある、ボウリングの 2 つのコードです。
入力（投球の配列）から出力（得点）への関数として書いた版と、オブジェクト指向でよくある形の版を、
Python 風の構文で書き直しました。

| ファイル | なでしこ3 | Python |
|---------|-----------|--------|
| 関数版 | `src/bowling.nako3` | `src/bowling.py` |
| オブジェクト指向版 | `src/bowling_oo.nako3` | `src/bowling_oo.py` |

### ボウリングの TODO リスト

得点の規則は、10 フレームの合計に、スペアなら次の 1 投、ストライクなら次の 2 投を加えるというものです。

- [ ] ガターゲーム（20 投すべて 0 ピン）は 0 点
- [ ] すべて 1 ピンなら 20 点
- [ ] スペアは次の 1 投を加算する
- [ ] ストライクは次の 2 投を加算する
- [ ] パーフェクトゲーム（12 投すべてストライク）は 300 点
- [ ] 2 つの `10` と分岐の意味を名前で表す（リファクタリング）
- [ ] オブジェクト指向版でも同じ得点になる

### テストデータを作る関数

20 投ぶんの配列をテストに直接書くと読みにくいため、配列の後ろに同じ値を N 個つなげる関数を用意します。

```python
def 同値連結処理(配列: list[int], PINS: int, N: int) -> list[int]:
    結果 = list(配列)
    for 番号 in range(1, N + 1):
        結果.append(PINS)
    return 結果
```

```text
●(配列とPINSとNで)同値連結処理とは:
    変数のF結果 = 配列複製(配列)
    # cnako3 の「繰り返す」は開始が終了より大きいと逆向きに回るため、0 件を先に返す
    もし(N < 1)ならば:
        F結果を戻す
    番号を1からNまで繰り返す:
        配列追加(F結果,PINS)
    F結果を戻す
```

`list(配列)` が `配列複製(配列)` に対応します。
どちらも元の配列をコピーしてから追加するので、引数に渡した配列は書き換わりません。

なでしこ3 にだけ `もし(N < 1)ならば:` の行があります。
Python の `range(1, 1)` は空なので、N が 0 のときループは 1 回も回りません。
なでしこ3 では、N が 0 のとき `1から0まで` が逆向きに回る処理系があるため、先に 0 件を返しています
（詳しくは後述の落とし穴「処理系によって範囲の向きが違う」で扱います）。
Python なら `配列 + [PINS] * N` と 1 行で書けますが、FizzBuzz と同じく、ここでも両言語の形をそろえています。

### ステップ 1〜2: ガターと 1 ピン（仮実装から三角測量）

ガターゲームのテストを `0を戻す` の仮実装で通し、「すべて 1 ピンなら 20 点」で一般化します。

```python
@pytest.mark.parametrize(
    ("投球列", "期待"),
    [
        pytest.param(同値連結処理([], 0, 20), 0, id="ガターゲームは0点"),

    ],

def test_得点計算処理(投球列: list[int], 期待: int) -> None:

```


ここまでは、投球の合計を返すだけで通ります。

```python
def 得点計算処理(投球列: list[int]) -> int:

```

```text
●(投球列の)得点計算処理とは:

```

### ステップ 3: スペア（フレームという単位の導入）

「スペアは次の 1 投を加算する」は、`[5, 5, 3]` のあとに 0 を 17 投つなげて 16 点を期待します。
合計のままでは 13 点になり、テストが失敗します。
投球を 1 つずつ見るのではなく、**フレーム** という単位で 10 回繰り返す形に変えます。

```python
def 得点計算処理(投球列: list[int]) -> int:
    得点 = 0
    位置 = 0
    for _ in range(10):
        if 投球列[位置] + 投球列[位置 + 1] == 10:
            得点 = 得点 + 10 + 投球列[位置 + 2]
        else:
            得点 = 得点 + 投球列[位置] + 投球列[位置 + 1]
        位置 = 位置 + 2
    return 得点
```

```text
●(投球列の)得点計算処理とは:
    変数のF得点 = 0
    変数のF位置 = 0
    10回、繰り返す:
        もし(投球列[F位置] + 投球列[F位置 + 1] = 10)ならば:
            F得点 = F得点 + 10 + 投球列[F位置 + 2]
        違えば:
            F得点 = F得点 + 投球列[F位置] + 投球列[F位置 + 1]
        F位置 = F位置 + 2
    F得点を戻す
```

ループ変数を使わない回数の繰り返しは、`for _ in range(10):` が `10回、繰り返す:` に対応します。
マニュアルの対照表にもある組み合わせです。
配列の添字は、どちらも 0 から始まり、`投球列[位置 + 1]` の形もそのまま同じです。

### ステップ 4〜5: ストライクとパーフェクトゲーム

「ストライクは次の 2 投を加算する」（`[10, 3, 4]` のあとに 0 を 16 投、合計 19 投）を加えると、ステップ 3 のコードでは失敗します。
ここで、両言語の失敗の仕方が分かれます。

```text
# Python
E   IndexError: list index out of range

# なでしこ3（gonako）
  NG: ストライクは次の2投を加算する: ASSERT失敗: 『NaN』と『24』が一致しません。
```

ストライクのフレームも 2 投ずつ進めるため、10 フレーム目で 19 投の配列の外（添字 19）を読みます。
Python は範囲外の添字で例外を投げて止まりますが、なでしこ3 は例外にならず、存在しない要素との足し算が `NaN` になって計算が続きます
（cnako3 でも `NaN !== 24` でした）。
今回は期待値との比較で気づけましたが、**範囲外の読み取りは処理系が止めてくれない** ことを覚えておく必要があります。

先頭にストライクの分岐を足します。
ストライクのフレームは 1 投で終わるため、位置は 1 だけ進めます。

```python
def 得点計算処理(投球列: list[int]) -> int:
    得点 = 0
    位置 = 0
    for _ in range(10):
        if 投球列[位置] == 10:
            得点 = 得点 + 10 + 投球列[位置 + 1] + 投球列[位置 + 2]
            位置 = 位置 + 1
        elif 投球列[位置] + 投球列[位置 + 1] == 10:
            得点 = 得点 + 10 + 投球列[位置 + 2]
            位置 = 位置 + 2
        else:
            得点 = 得点 + 投球列[位置] + 投球列[位置 + 1]
            位置 = 位置 + 2
    return 得点
```

```text
●(投球列の)得点計算処理とは:
    変数のF得点 = 0
    変数のF位置 = 0
    10回、繰り返す:
        もし(投球列[F位置] = 10)ならば:
            F得点 = F得点 + 10 + 投球列[F位置 + 1] + 投球列[F位置 + 2]
            F位置 = F位置 + 1
        違えばもし(投球列[F位置] + 投球列[F位置 + 1] = 10)ならば:
            F得点 = F得点 + 10 + 投球列[F位置 + 2]
            F位置 = F位置 + 2
        違えば:
            F得点 = F得点 + 投球列[F位置] + 投球列[F位置 + 1]
            F位置 = F位置 + 2
    F得点を戻す
```

14 行が 1 行ずつ対応しています。
違うのは、ローカル変数の `変数の` と `F`、比較の `=` と `==` だけです。

最後の「パーフェクトゲームは 300 点」（10 を 12 投）は、コードを変えずに最初から通ります。
10 フレーム目のボーナス投球を、11 投目と 12 投目として先読みしているためです。
新しい振る舞いを足すテストではなく、境界の振る舞いを確かめるテストとして残します。

### ステップ 6: リファクタリングで意図を明確にする

テストはすべて通りましたが、`得点計算処理` にはまだ読み手に推測を強いる箇所が残っています。

- `10` が 2 つの意味（1 ゲームのフレーム数と、1 フレームのピン数）で使われている
- `投球列[位置] = 10` が「ストライク」を、`投球列[位置] + 投球列[位置 + 1] = 10` が「スペア」を意味することが、名前ではなく式で表されている
- 3 つの分岐が、それぞれ違う形の足し算をしていて、共通の構造が見えない

同じ演習リポジトリの Kotlin 版サンプル（`BowlingGame.kt`）は、この 3 点を次のように解決しています（コード全体はこのあとの「参考」で紹介します）。

1. 2 つの `10` に、`FRAMES_PER_GAME` と `ALL_PINS` という別々の名前を付ける
2. ストライクとスペアの判定を、`isStrike` と `isSpare` という名前の関数に切り出す
3. 3 つの分岐を「そのフレームで使う投球数」と「ボーナスとして加える投球数」の 2 つの数の違いとして捉え直し、`frameScore(rollsUsed, bonusRolls)` という 1 つの関数にまとめる

3 つ目が要です。
ストライクは「1 投使って 2 投ボーナス」、スペアは「2 投使って 1 投ボーナス」、それ以外は「2 投使ってボーナスなし」です。
得点は、どの場合も **使う投球数 + ボーナス投球数** の分だけ先頭から足した値になります。
分岐ごとに違っていた足し算が、2 つの数の違いだけになります。

Kotlin 版はさらに、可変の変数を使わない再帰で書いています。ここでは、ここまでの添字と繰り返しの形を保ったまま、この 3 点だけを取り入れます。
テストには手を入れません。
テストを変えずに実装の構造だけを変え、テストが通り続けることを確かめるのがリファクタリングです。

```python
from typing import Final

フレーム総数: Final = 10
全ピン数: Final = 10


def 得点計算処理(投球列: list[int]) -> int:
    得点 = 0
    位置 = 0
    for _ in range(フレーム総数):
        if ストライク判定処理(投球列, 位置):
            得点 = 得点 + フレーム得点処理(投球列, 位置, 投球数=1, ボーナス数=2)
            位置 = 位置 + 1
        elif スペア判定処理(投球列, 位置):
            得点 = 得点 + フレーム得点処理(投球列, 位置, 投球数=2, ボーナス数=1)
            位置 = 位置 + 2
        else:
            得点 = 得点 + フレーム得点処理(投球列, 位置, 投球数=2, ボーナス数=0)
            位置 = 位置 + 2
    return 得点


def ストライク判定処理(投球列: list[int], 位置: int) -> bool:
    return 投球列[位置] == 全ピン数


def スペア判定処理(投球列: list[int], 位置: int) -> bool:
    return 投球列[位置] + 投球列[位置 + 1] == 全ピン数


def フレーム得点処理(投球列: list[int], 位置: int, 投球数: int, ボーナス数: int) -> int:
    """そのフレームで使う投球数と、ボーナスとして加算する投球数の合計を足す"""
    return sum(投球列[位置 : 位置 + 投球数 + ボーナス数])
```

```text
定数のフレーム総数 = 10
定数の全ピン数 = 10

●(投球列の)得点計算処理とは:
    変数のF得点 = 0
    変数のF位置 = 0
    (フレーム総数)回、繰り返す:
        もし(ストライク判定処理(投球列,F位置))ならば:
            F得点 = F得点 + フレーム得点処理(投球列,F位置,1,2)
            F位置 = F位置 + 1
        違えばもし(スペア判定処理(投球列,F位置))ならば:
            F得点 = F得点 + フレーム得点処理(投球列,F位置,2,1)
            F位置 = F位置 + 2
        違えば:
            F得点 = F得点 + フレーム得点処理(投球列,F位置,2,0)
            F位置 = F位置 + 2
    F得点を戻す

●(投球列と位置の)ストライク判定処理とは:
    (投球列[位置] = 全ピン数)を戻す

●(投球列と位置の)スペア判定処理とは:
    (投球列[位置] + 投球列[位置 + 1] = 全ピン数)を戻す

# そのフレームで使う投球数と、ボーナスとして加算する投球数の合計を足す
●(投球列と位置と投球数とボーナス数で)フレーム得点処理とは:
    変数のF合計 = 0
    番号を位置から(位置 + 投球数 + ボーナス数 - 1)まで繰り返す:
        F合計 = F合計 + 投球列[番号]
    F合計を戻す
```

`得点計算処理` は、「ストライクなら 1 投使って 2 投ボーナス」と、規則の文章に近い形で読めるようになりました。
両言語とも、関数を使う位置より後ろで定義しても動きます。
そのため、全体の流れを上に、細部を下に置けます。
リファクタリングの前後で、テストは両言語とも全件通ったままです。

並べると、両言語の違いが 3 つ見えてきます。

**定数**: Python の `Final` は型の注釈で、守らせるのは mypy です。
`フレーム総数 = 11` と再代入すると、mypy は `Cannot assign to final name "フレーム総数"` と指摘しますが、実行すると何事もなく 11 になります。
なでしこ3 の `定数の` は処理系が守ります。
再代入すると、実行時に `定数『…フレーム総数』は既に定義済みなので、値を代入することはできません。` という文法エラーで止まります（gonako・cnako3 とも同じ）。
ただし `gonako lint` はこの誤りを報告しません。

**引数の名前**: Python はキーワード引数で `投球数=1, ボーナス数=2` と書けるので、Kotlin の `rollsUsed = 1, bonusRolls = 2` と同じく、呼び出し側で数の意味が読めます。
本章のなでしこ3 の関数呼び出しは助詞の順に値を並べるだけなので、`フレーム得点処理(投球列,F位置,1,2)` の `1,2` が何の数かは、定義を見ないと分かりません。
意図を名前で伝えるという点では、ここは Python 風の書き方の弱いところです。

**部分列の合計**: Python はスライスで `sum(投球列[位置 : 位置 + 投球数 + ボーナス数])` と 1 行で書けます。
なでしこ3 では繰り返しで足しています（終了値を含むため `- 1` が要ります）。
ここで繰り返しの開始が終了を超えることはありません。
投球数とボーナス数の合計は、ストライクとスペアで 3、それ以外で 2 なので、範囲は常に 2 件以上になるためです。

### 参考: Kotlin によるエレガントな関数型実装

ステップ 6 で手本にした Kotlin 版の全体を紹介します。
演習リポジトリ [k2works/from-objects-to-functions-excersice](https://github.com/k2works/from-objects-to-functions-excersice)（関数型ソフトウェア設計の理論と実践）にあるサンプルで、
[`BowlingGame.kt`](https://github.com/k2works/from-objects-to-functions-excersice/blob/main/apps/kotlin/zettai/zettai-step1-http/src/main/kotlin/zettai/BowlingGame.kt) がそのファイルです。
本シリーズの Kotlin の Nix 環境で、付属のテスト（関数版 5 件、オブジェクト指向版 1 件）が通ることを確認しました。

```kotlin
/**
 * ボウリング 1 ゲームの得点を返す。
 *
 * 投球の並びを受け取って点数を返すだけの純粋関数として書く。
 * ゲームの途中経過を保持するオブジェクトを作らないので、
 * テストは「入力を与えて出力を確かめる」形だけで済む。
 */
fun scoreOf(rolls: List<Int>): Int = scoreFrames(rolls, remainingFrames = FRAMES_PER_GAME)

private const val FRAMES_PER_GAME = 10
private const val ALL_PINS = 10

private fun scoreFrames(rolls: List<Int>, remainingFrames: Int): Int =
    when {
        remainingFrames == 0 -> 0
        rolls.isStrike() -> rolls.frameScore(rollsUsed = 1, bonusRolls = 2) + rolls.nextFrames(1, remainingFrames)
        rolls.isSpare() -> rolls.frameScore(rollsUsed = 2, bonusRolls = 1) + rolls.nextFrames(2, remainingFrames)
        else -> rolls.frameScore(rollsUsed = 2, bonusRolls = 0) + rolls.nextFrames(2, remainingFrames)
    }

private fun List<Int>.isStrike(): Boolean = first() == ALL_PINS

private fun List<Int>.isSpare(): Boolean = take(2).sum() == ALL_PINS

/** そのフレームで使う投球数と、ボーナスとして加算する投球数の合計を足す。 */
private fun List<Int>.frameScore(rollsUsed: Int, bonusRolls: Int): Int = take(rollsUsed + bonusRolls).sum()

private fun List<Int>.nextFrames(rollsUsed: Int, remainingFrames: Int): Int =
    scoreFrames(drop(rollsUsed), remainingFrames - 1)
```

関数はどれも `=` の右に式を 1 つ書くだけで、`var` は 1 つもありません。
ステップ 6 のリファクタリング後のコードと比べると、何がエレガントなのかが見えてきます。

| 観点 | ステップ 6（Python・なでしこ3） | Kotlin 版 |
|------|-------------------------------|-----------|
| 得点の累積 | 可変の変数 `得点`・`F得点` に足し込む | 「このフレームの得点 + 残りのフレームの得点」という式の値 |
| 今どこを見ているか | 可変の添字 `位置`・`F位置` を進める | `drop(rollsUsed)` で使い終えた投球を除いたリストを次に渡す |
| 何フレーム目か | `range(フレーム総数)`・`(フレーム総数)回` の繰り返し | 引数 `remainingFrames` を 1 ずつ減らし、0 になったら 0 点 |
| 分岐 | `if` 文で変数を書き換える | `when` 式が値を返す |
| 判定の書き方 | `ストライク判定処理(投球列, 位置)` | 拡張関数 `rolls.isStrike()` |
| 数の意味 | Python はキーワード引数、なでしこ3 は位置で渡す | 名前付き引数 `rollsUsed = 1, bonusRolls = 2` |

読みどころは 4 つあります。

**規則がそのまま定義になっている**: `scoreFrames` は「残りが 0 フレームなら 0 点。そうでなければ、最初のフレームの得点に、残りのフレームの得点を足す」と読めます。
ボウリングの得点の規則を、そのまま再帰の定義として書き下した形です。
ループ版では、読み手が `位置` と `得点` の変化を頭の中で追う必要がありました。
Kotlin 版では、各行が「このフレームの得点は何か」だけを述べています。

**状態がリストそのものに入っている**: ループ版の `位置` は、「投球列のどこまでを使い終えたか」という状態でした。
Kotlin 版は、使い終えた投球を `drop` で取り除いたリストを次の呼び出しに渡します。
そのため、どの関数も常に「リストの先頭」だけを見れば済みます。
`isStrike` が `first()`、`isSpare` が `take(2)` と短く書けるのはこのためです。
添字の計算（`位置 + 1`・`位置 + 2`）が、コードから消えています。

**ボーナスは「消費しない先読み」**: `frameScore` は `rollsUsed + bonusRolls` 投ぶんを `take` で読みますが、次に渡すリストからは `rollsUsed` 投しか `drop` しません。
ボーナスの投球は、読んでも消費しない。
この非対称が、ストライク・スペア・10 フレーム目のボーナス投球を、場合分けなしで正しく扱う仕掛けになっています。

**主語が先に来る**: `rolls.isStrike()` や `rolls.frameScore(…)` は拡張関数で、対象（投球列）が先、操作が後に来ます。
なでしこ3 の `投球列の得点計算` と同じ語順です。
[第 9 章](09-japanese-implementation-column.md)で Kotlin が「語順の再現」で満点だったのも、同じ拡張関数（`infix` を付けた拡張関数）によるものでした。

本章の Python 風の書き方がこの形を採らなかったのは、比べる相手の Python が添字と繰り返しで書くのが一般的だからです。
なお、Python でも `sum(投球列[:使う投球数 + ボーナス投球数])` と `得点計算処理(投球列[使う投球数:], 残りフレーム数 - 1)` を組み合わせれば、同じ再帰の形で書けます（手元で 5 つのテストケースが同じ得点になることを確かめました）。
一方、なでしこ3 では、Python のスライスや Kotlin の `drop` に当たる、処理系をまたいで使える書き方を本章では確かめられませんでした
（gonako の `配列範囲コピー` は範囲を `{先頭, 末尾}` の辞書で受け取る作りで、cnako3 での互換性は未確認です）。
`drop` に当たる処理を自分で書くことになるため、この形はなでしこ3 では Kotlin ほど簡潔になりません。
ループ版から関数型の書き方へ進む次の一歩として、Kotlin 版を読んでみることをすすめます。

### オブジェクト指向版: クラスと辞書

Python では、投球を貯める状態をインスタンスに持たせるクラスとして書きます。

```python
class ゲーム:
    def __init__(self) -> None:
        self.投球列: list[int] = []

    def 投球処理(self, PINS: int) -> None:
        self.投球列.append(PINS)

    def 連続投球処理(self, PINS: int, N: int) -> None:
        for 番号 in range(1, N + 1):
            self.投球処理(PINS)

    def 得点取得処理(self) -> int:
        return 得点計算処理(self.投球列)
```

なでしこ3 にはクラス構文がありません。
状態を辞書に持たせ、その辞書を最初の引数で受け取って書き換える関数を並べます。

```text
●ゲーム作成処理とは:
    {「投球列」: []}を戻す

●(ゲームとPINSで)投球処理とは:
    配列追加(ゲーム[「投球列」],PINS)

●(ゲームとPINSとNで)連続投球処理とは:
    もし(N < 1)ならば:
        戻る
    番号を1からNまで繰り返す:
        投球処理(ゲーム,PINS)

●(ゲームの)得点取得処理とは:
    得点計算処理(ゲーム[「投球列」])を戻す
```

対応は次のとおりです。

| Python | なでしこ3 |
|--------|-----------|
| `class ゲーム:` と `__init__` | `ゲーム作成処理` が辞書を返す |
| `self.投球列` | `ゲーム[「投球列」]` |
| `def 投球処理(self, PINS):` | `●(ゲームとPINSで)投球処理とは:` |
| `対象ゲーム.投球処理(5)` | `投球処理(ゲーム,5)` |

Python のメソッドも、定義では `self` を最初の引数として明示します。
なでしこ3 の `投球処理(ゲーム,5)` は、Python の `ゲーム.投球処理(対象ゲーム, 5)`（クラスから関数として呼ぶ形）と同じ並びです。
クラス構文は、この「状態を最初の引数で渡す」書き方に名前と置き場所を与えたもの、と読むこともできます。

テストは、状態を作る準備の行が増えます。

```python
def test_オブジェクト指向版もスペアを加算する() -> None:
    対象ゲーム = ゲーム()
    対象ゲーム.投球処理(5)
    対象ゲーム.投球処理(5)
    対象ゲーム.投球処理(3)
    対象ゲーム.連続投球処理(0, 17)
    assert 対象ゲーム.得点取得処理() == 16
```

```text
ゲーム = ゲーム作成処理
投球処理(ゲーム,5)
投球処理(ゲーム,5)
投球処理(ゲーム,3)
連続投球処理(ゲーム,0,17)
検証処理(「オブジェクト指向版もスペアを加算する」,得点取得処理(ゲーム),16)
```

もう 1 つ、2 つ目のゲームを作っても最初のゲームの状態が変わらないことを確かめるテストを置いています。
`ゲーム作成処理` の辞書リテラルは呼ぶたびに新しい辞書と配列を作るので、2 つのゲームは投球列を共有しません。
Python の `__init__` で `self.投球列 = []` と書くのと同じ振る舞いです。

関数版のテストは「何を渡すと何が返るか」の 1 行で済みますが、オブジェクト指向版は状態を作る準備が要ります。
両方とも得点の計算そのものは `得点計算処理` に任せており、オブジェクト指向版は投球を貯めるだけの薄い殻になっています。
この関係は、Python でもなでしこ3 でも変わりません。

## 並べて分かった違い

| 観点 | Python | なでしこ3（Python 風） | 差 |
|------|--------|----------------------|----|
| ブロック | `:` と字下げ | `:` と字下げ | なし |
| 分岐 | `if` / `elif` / `else` | `もし…ならば:` / `違えばもし…ならば:` / `違えば:` | 単語だけ |
| 戻り値 | `return 値` | `値を戻す` | 語順（文頭と文末） |
| 等価比較 | `==` | `=` | 記号 |
| 範囲 | `range(1, N + 1)`（終了値を含まない） | `1からNまで`（終了値を含む） | **意味** |
| 開始が終了より大きい範囲 | 空 | 処理系によって逆向きに回る（cnako3）か、回らない（gonako） | **意味** |
| 回数の繰り返し | `for _ in range(10):` | `10回、繰り返す:` | 単語だけ |
| 定数 | `Final`（mypy が検査し、実行時は止めない） | `定数の`（実行時に処理系が止める） | 守らせる仕組み |
| 引数の名前 | キーワード引数 `投球数=1` | 位置で渡す `1,2` | 読みやすさ |
| 反復 | `for 値 in リスト:` | `値でリストを反復:` | 語順 |
| 結合 | `",".join(リスト)` | `配列結合(リスト,「,」)` | 引数の順 |
| リスト内包表記 | あり | なし | 構文の有無 |
| クラス | `class` と `self` | 辞書と、辞書を最初の引数で受け取る関数 | 構文の有無 |
| メソッド呼び出し | `ゲーム.投球処理(5)` | `投球処理(ゲーム,5)` | 語順 |
| テスト | pytest | 自作の `検証処理` と `gonako doctest` | 標準の有無 |
| 型の区別 | `"1" == 1` は偽 | `ASSERT等` は `「1」` と `1` を同一視 | 意味 |
| 範囲外の添字 | `IndexError` で止まる | 例外にならず、計算結果が `NaN` になる | **意味** |

差の多くは単語と語順で、Python を知っていれば推測できる範囲です。
注意が要るのは **意味が違う 4 か所**（範囲の終了値、開始が終了より大きい範囲、比較での型の扱い、範囲外の添字）で、いずれもテストで捕まえられました。

## 落とし穴

### コロンの直後に処理を書く

Python では `if A > 3: print("大きい")` と 1 行で書けますが、なでしこ3 の Python 風構文ではコロンの後に改行が必要です。

```text
もし(A > 3)ならば: 「大きい」と表示
```

```text
[文法エラー]e2.nako3(2行目): 構文解析でエラー。『:』の使い方が間違っています。
```

1 行で書きたい場合は、本編の `もし、A > 3ならば,「大きい」と表示` の形を使います。

### インデントを忘れてもエラーにならない

Python では、コロンの次の行を字下げし忘れると `IndentationError` になります。
`gonako` v3.8.8 では、字下げを忘れた行はブロックの外の文として扱われ、エラーになりません。

```text
A = 1
もし(A > 3)ならば:
「大きい」と表示
「おわり」と表示
```

```text
大きい
おわり
```

`A` は 1 なので条件は成立していませんが、「大きい」が表示されています。
`gonako lint` も「文法エラーはありません」と報告します。
**見た目は Python でも、Python ほど字下げに厳格ではない**ため、振る舞いをテストで確かめることが Python 以上に大切です。

### 処理系によって範囲の向きが違う

マニュアルは、開始値を終了値より大きくすると逆順に繰り返せると説明しています（回文判定のサンプル）。
同じコードを 2 つの処理系で実行すると、結果が分かれました。

```text
番号を3から1まで繰り返す:
    継続表示(番号 & 「,」)
「」を表示
```

| 書き方 | cnako3 v3.8.7 | gonako v3.8.8 | Python の対応 |
|--------|---------------|---------------|--------------|
| `3から1まで` | `3,2,1` と逆順に回る | 1 回も回らない | `range(3, 0, -1)` なら逆順 |
| `1からNまで`（N = 0） | `1,0` と 2 回回る | 1 回も回らない | `range(1, 1)` は空 |

ボウリングの `同値連結処理` から `もし(N < 1)ならば:` のガードを外すと、
gonako ではテストがすべて通りますが、cnako3 では「0 件の連結は元の配列のまま」が失敗します。

```text
  NG: 0件の連結は元の配列のまま: Expected values to be strictly equal:

'1,2,9,9' !== '1,2'
```

N が 0 のとき、`1から0まで` が 1 と 0 の 2 回回り、9 が 2 つ追加されています。
Python の `range` に慣れていると、N が 0 なら回らないと思い込みがちです。
**N が 0 になりうる範囲の繰り返しには、処理系に依らないようガードを置き、0 件のテストを書いておく** と安全です。

### 命令名と変数名の衝突

マニュアルは、`合計`・`対象`・`回数` などを変数名に使うと標準命令や特殊変数と衝突することがあると注意しています。
関数名の末尾に「処理」を付け、ローカル変数に `F` を付ける規則は、この衝突を避けるためのものです。
本章のコードでも `FizzBuzz変換処理`・`変数のF結果` と、この規則に従っています。

### 助詞を含む変数名

マニュアルは、助詞を含む変数名も避けるよう注意しています。
ボウリングのテストを書いている途中で、2 つ目のゲームを `別のゲーム` と名付けたところ、文法エラーになりました。

```text
別のゲーム = ゲーム作成処理
```

```text
[文法エラー]test/bowling_oo_test.nako3(11行目): 不完全な文です。単語『bowling_oo_test__別』、演算子『＝』が解決していません。演算子『＝』は『単語『bowling_oo_test__ゲーム』と関数『bowling_oo__ゲーム作成処理』が等しいかどうかの比較』として使われています。
```

「の」が助詞として読まれ、`別` と `ゲーム` の 2 語に分かれています。
さらに、行頭の代入のつもりだった `=` が、`ゲーム` と `ゲーム作成処理` の比較として解釈されています。
代入と比較に同じ `=` を使うなでしこ3 ならではのエラーです（gonako・cnako3 とも同じメッセージでした）。
Python では `別のゲーム = ゲーム()` は普通の代入なので、Python の感覚で名前を付けるとつまずきます。
本章では `ゲーム2` に改めました。

## 考察: Python への橋渡しとしてのなでしこ3

マニュアルの狙いは、なでしこ3 で学んだ人が Python へ移るとき、**制御構造の形を学び直さずに済む** ことです。
FizzBuzz とボウリングゲームを TDD で並べてみると、その狙いはおおむね達成されていました。
分岐・反復・関数定義の骨格は 1 行ずつ対応し、違いは単語と語順に収まります。
マニュアルの言葉を借りれば、なでしこ3 のコードは「仕様書とプログラムの距離を縮め」ます。
Python 風に書けば、その距離を保ったまま、プログラムと Python の距離も縮められます。

一方で、Python 風にすると失われるものもあります。

- **助詞による引数**: `配列結合(リスト,「,」)` は、本編の `リストを「,」で配列結合` に比べて、どちらが区切り文字かが字面から読み取りにくくなります
- **文としての読みやすさ**: 本編の `Nを文字列変換して戻す` は日本語の文として読めますが、`文字列変換(N)を戻す` は関数呼び出しに日本語の語尾が付いた形になります
- **誤りの検出**: 見た目は Python と同じでも、字下げの誤りや範囲外の添字を処理系が検出してくれません
- **引数の名前**: Python のキーワード引数のように呼び出し側で数の意味を示せないため、ボウリングの `フレーム得点処理(投球列,F位置,1,2)` は定義を見ないと読めません
- **クラス**: クラス構文がないため、オブジェクト指向版は辞書と関数で組み立てることになります。ただし、得点の計算を状態のない関数に切り出しておけば、その差は薄い殻の部分に閉じ込められます

[第 9 章](09-japanese-implementation-column.md)は、他の言語がなでしこ3 に近づこうとすると代償があることを示しました。
本章は逆向きにも代償があることを示しています。
どちらに寄せるかは、読み手と目的で決めます。
日本語で考えて仕様を書くことが目的なら本編の書き方、Python へ進む準備が目的なら Python 風の書き方が向いています。
TDD のテストは、どちらの書き方でも同じ日本語の文章で書けるため、書き方を切り替えても仕様として読めます。
