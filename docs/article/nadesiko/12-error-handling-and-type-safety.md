# 第 12 章: エラーハンドリングと型安全性

## 12.1 はじめに

第 4 部の締めくくりとして、エラーを **値として返す** 結果辞書（Result 相当）、`空` による欠損の表現（Option 相当）、そして動的型付け言語であるなでしこ3 で実行時の型チェックによって安全性を担保する方法を学びます。

なでしこ3 には、`「…」のエラー発生` でエラーを起こし、`エラー監視 … エラーならば … ここまで` で捕まえる例外の仕組みがあります。第 2 章のテスト補助 `検証` や、第 3 部のタイプの生成（存在しない番号でエラーを発生させる）ですでに使ってきました。本章では、それとは別に、成功と失敗を **辞書の値** として返すやり方を TDD で実装し、両者を使い分けます。

### この章で学ぶこと

- 成功と失敗を辞書で表す `成功結果` / `失敗結果`（Result 相当）
- `変数型確認` による動的な型チェックと、0 以下を拒否する `安全変換`
- 失敗時にエラーを発生させる `厳格変換` と、`エラー監視` による捕捉
- `空` を受け付ける `空許容変換`（Option 相当）と、その落とし穴
- `ASSERT等` が緩い比較であることの再確認と、テスト補助で型を比べる意味
- 動的型付け言語での型安全性の考え方と、第 4 部・シリーズ全体の振り返り

## 12.2 例外と「エラーを値として返す」アプローチ

例外は、エラーが起きた場所から `エラー監視` まで処理を一気に飛ばします。通常の流れから外れた失敗を扱うには便利ですが、呼び出し側が `エラー監視` を書き忘れると、プログラムはそこで止まってしまいます。

これに対して、成功と失敗を **値** として返すのが Result のアプローチです。Kotlin や Rust には `Result` 型がありますが、なでしこ3 にはクラス構文も独自の型を定義する仕組みもありません。そこで、第 3 部の値オブジェクトと同じく **辞書** を使います。

```text
成功: {"成功": はい, "値": 変換結果}
失敗: {"成功": いいえ, "エラー": メッセージ}
```

戻り値の `"成功"` を見れば、呼び出し側は必ず失敗の可能性に気付けます。

**TODO リスト**:

- [ ] 0 以下は失敗の結果辞書を返す（`失敗結果`）
- [ ] 数値以外は失敗の結果辞書を返す（動的な型チェック）
- [ ] 失敗時にエラーを発生させる `厳格変換`
- [ ] `空` を受け付ける `空許容変換`

実装は `src/error.nako3` に置き、テストは `test/error_test.nako3` に書きます。

## 12.3 成功結果と安全変換

### Red: 正の数は成功になる

```nako3
!「./helper.nako3」を取り込む
!「../src/error.nako3」を取り込む

結果 = 3を安全変換
「正の数は成功になる」と結果["成功"]と(はい)で検証
「成功結果は値を持つ」と結果["値"]と「Fizz」で検証
テスト結果報告
```

```nako3
# エラーハンドリング（例外と結果辞書）
!「./fizzbuzz.nako3」を取り込む
```

```bash
$ gonako run test/error_test.nako3
[文法エラー]test/error_test.nako3(4行目): 未解決の単語があります: [数値3を]
次の命令の可能性があります:

```

### Green: 成功結果を返す

まずは成功の場合だけを実装します。

```nako3
# エラーハンドリング（例外と結果辞書）
!「./fizzbuzz.nako3」を取り込む

●(値の)成功結果
    {"成功": はい, "値": 値}を戻す
ここまで

●(Nを)安全変換
    (NをFizzBuzz変換)の成功結果を戻す
ここまで
```

```bash
$ gonako run test/error_test.nako3
  ok: 正の数は成功になる
  ok: 成功結果は値を持つ
  2件成功、0件失敗
```

`(NをFizzBuzz変換)の成功結果を戻す` は「N を FizzBuzz 変換したものの成功結果を戻す」と読めます。`●(値の)成功結果` のように助詞「の」で引数を受け取る関数は、`〜の成功結果` と名詞句のように呼び出せます。

## 12.5 動的な型チェック — 数値以外を拒否する

### Red: 数値以外は失敗になる

なでしこ3 は動的型付けの言語なので、`安全変換` には文字列も渡せてしまいます。

```nako3
結果 = 「abc」を安全変換
「数値以外は失敗になる」と結果["エラー"]と「数値を指定してください: abc」で検証
```

```bash
$ gonako run test/error_test.nako3
  ok: 正の数は成功になる
  ok: 成功結果は値を持つ
  ok: 0は失敗になる
  ok: 失敗結果はエラーを持つ
  NG: 数値以外は失敗になる: ASSERT失敗: 『undefined』と『string』が一致しません。
  4件成功、1件失敗
[実行時エラー]test/error_test.nako3(20行目): 1件のテストが失敗しました
```

`エラー` が `undefined` ということは、失敗結果ではなかったということです。実際に何が返っているのかを `JSONエンコード` で表示してみます（型チェックを入れる前の `error.nako3` を `src/error_mid.nako3` として保存し、それを取り込んでいます）。

```nako3
!「./src/error_mid.nako3」を取り込む

(「abc」を安全変換)をJSONエンコードして表示
```

```bash
$ gonako run abc_demo.nako3
{"成功":true,"値":"abc"}
```

`「abc」 ≦ 0` は成り立たないので 0 以下のチェックをすり抜け、`FizzBuzz変換` でもどの倍数の条件にも当たらず、`"abc"` が **成功** として返ってきました。静的型付けの言語ならコンパイル時に弾かれる誤りが、動的型付けの言語では黙って通ってしまいます。

### Green: 変数型確認で型をチェックする

```nako3
●(Nを)安全変換
    もし、(Nの変数型確認) ≠ 「number」ならば
        「数値を指定してください: {N}」の失敗結果を戻す
    ここまで
    もし、N ≦ 0ならば
        「正の数を指定してください: {N}」の失敗結果を戻す
    ここまで
    (NをFizzBuzz変換)の成功結果を戻す
ここまで
```

```bash
$ gonako run test/error_test.nako3
  ok: 正の数は成功になる
  ok: 成功結果は値を持つ
  ok: 0は失敗になる
  ok: 失敗結果はエラーを持つ
  ok: 数値以外は失敗になる
  5件成功、0件失敗
```

関数の入口で `変数型確認` により型を調べ、`number` 以外なら失敗結果を返します（`!=` は整形で `≠` になります）。これは **ガード節** による動的な型チェックです。4 通りの入力で結果辞書を確かめてみましょう。

```nako3
!「./src/error.nako3」を取り込む

(3を安全変換)をJSONエンコードして表示
(0を安全変換)をJSONエンコードして表示
(「abc」を安全変換)をJSONエンコードして表示
(「3」を安全変換)をJSONエンコードして表示
```

```bash
$ gonako run result_demo.nako3
{"成功":true,"値":"Fizz"}
{"成功":false,"エラー":"正の数を指定してください: 0"}
{"成功":false,"エラー":"数値を指定してください: abc"}
{"成功":false,"エラー":"数値を指定してください: 3"}
```

文字列の `「3」` も、数値ではないので失敗になります。`ASSERT等` のように数値と文字列を区別しない比較に頼らず、型を明示的に調べているからです。

## 12.6 厳格変換 — エラーを発生させる

結果辞書は失敗を無視しにくい反面、呼び出すたびに `"成功"` を確かめる必要があります。失敗したらそれ以上処理を続けられない場面では、例外のほうが簡潔です。`安全変換` の結果を例外に変換する `厳格変換` を作ります。

### Red: 厳格変換のテスト

```nako3
「厳格変換は値を返す」と(15を厳格変換)と「FizzBuzz」で検証
メッセージ = 「」
エラー監視
    -1を厳格変換
エラーならば
    メッセージ = エラーメッセージ
ここまで
「厳格変換は失敗時にエラーを発生させる」とメッセージと「正の数を指定してください: -1」で検証
```

```bash
$ gonako run test/error_test.nako3
[文法エラー]test/error_test.nako3(18行目): 不完全な文です。数値-1、単語『error_test__厳格変換』が解決していません。
```

### Green: 厳格変換の実装

```nako3
●(Nを)厳格変換
    結果 = Nを安全変換
    もし、結果["成功"]ならば、結果["値"]を戻す
    結果["エラー"]のエラー発生
ここまで
```

```bash
$ gonako run test/error_test.nako3
  ok: 正の数は成功になる
  ok: 成功結果は値を持つ
  ok: 0は失敗になる
  ok: 失敗結果はエラーを持つ
  ok: 数値以外は失敗になる
  ok: 厳格変換は値を返す
  ok: 厳格変換は失敗時にエラーを発生させる
  7件成功、0件失敗
```

`厳格変換` は検査のロジックを持たず、`安全変換` に委ねています。成功なら値を返し、失敗ならエラーメッセージで `エラー発生` します。結果辞書と例外を相互に変換できるようにしておけば、場面に応じて使い分けられます。`エラー監視` を書き忘れるとどうなるかも確かめておきましょう。

```nako3
!「./src/error.nako3」を取り込む

-1を厳格変換
「ここには来ない」を表示
```

```bash
$ gonako run strict_demo.nako3
[実行時エラー]strict_demo.nako3(25行目): 正の数を指定してください: -1
```

プログラムはそこで止まり、以降の `表示` は実行されません（行番号は取り込んだ `error.nako3` 側の `エラー発生` の位置です）。例外を使うなら捕まえる責任が呼び出し側に生じる、ということです。

### 学習用テスト: 空の正体

`空` とはいったい何なのか、学習用テストで調べてみます。

```nako3
!「./src/error.nako3」を取り込む

(空の変数型確認)を表示
(0 = 空)を表示
X = 0を空許容変換
「0を空許容変換: [{X}]」を表示
```

```bash
$ gonako run option_demo.nako3
string
true
0を空許容変換: []
```

`空` の型は `string`、つまり **空文字列** でした。他言語の `null` や `None` のような「値が無いことを表す専用の値」ではありません。さらに、`=` による比較は型を区別しないため `0 = 空` が `true` になり、`0を空許容変換` は FizzBuzz 変換されずに `空` を返しました。

動的型付けの言語では、**比較演算がどこまで型を区別するのか** を知らないと、Option のつもりの判定が別の値まで飲み込んでしまいます。学習用テストで見つけた問題は、そのままテストにして直しましょう。

### Red: 0 は空として扱わない

`0` は 15 の倍数なので、`0を空許容変換` は `「FizzBuzz」` を返すべきです。このことをテストに追加します。

```nako3
「0は空として扱わずに変換する」と(0を空許容変換)と「FizzBuzz」で検証
```

```bash
$ gonako run test/error_test.nako3
...
  ok: 空を渡すと空を返す
  ok: 数値を渡すと変換する
  NG: 0は空として扱わずに変換する: ASSERT失敗: 『』と『FizzBuzz』が一致しません。
  9件成功、1件失敗
[実行時エラー]test/error_test.nako3(20行目): 1件のテストが失敗しました
```

学習用テストで見た通り、`0` が `空` とみなされて空文字列が返っています（Red）。

### Green: 型も確かめてから空と判定する

`空` の正体は空文字列なので、「型が `string` で、かつ `空` と等しい」ときだけ空とみなすようにします。

```nako3
●(Nを)空許容変換
    もし、(Nの変数型確認) = 「string」 かつ N = 空ならば、空を戻す
    NをFizzBuzz変換して戻す
ここまで
```

```bash
$ gonako run test/error_test.nako3
...
  ok: 空を渡すと空を返す
  ok: 数値を渡すと変換する
  ok: 0は空として扱わずに変換する
  10件成功、0件失敗
```

`かつ` で 2 つの条件を組み合わせ、型の確認を比較の前に置きました。緩い比較 `=` を使うときは、**先に型をそろえてから値を比べる** のが、動的型付けの言語で意図しない一致を防ぐ基本的な手立てです。

## 12.8 ASSERT等 は緩い比較 — テスト補助で型を比べる意味

同じ問題はテストにもあります。第 2 章で確かめたとおり、`ASSERT等` は数値と文字列を区別しません。

```nako3
!「./helper.nako3」を取り込む

3と「3」がASSERT等
「ASSERT等だけなら数値3と文字列3は通ってしまう」を表示
「型も比べる」と3と「3」で検証
テスト結果報告
```

```bash
$ gonako run test/type_demo.nako3
ASSERT等だけなら数値3と文字列3は通ってしまう
  NG: 型も比べる: ASSERT失敗: 『number』と『string』が一致しません。
  0件成功、1件失敗
[実行時エラー]test/type_demo.nako3(20行目): 1件のテストが失敗しました
```

`ASSERT等` 単体では数値 `3` と文字列 `「3」` が等しいとみなされますが、第 2 章でリファクタリングしたテスト補助 `検証` は、値の前に `変数型確認` の結果を比べるので、型の取り違えを検出できます。

本章のテストでも、この仕組みが効いていました。`空許容変換` の Red で `『undefined』と『string』` と表示されたのは、未実装の関数が返す `undefined` と期待値の文字列とを、型の段階で区別できたからです。`「空を渡すと空を返す」と(空を空許容変換)と空で検証` のテストも、実際の値と期待値の **両方が空文字列（`string`）である** ことまで確かめています。型を持たない言語だからこそ、**テストが型の番人になる** のです。

## 12.9 動的型付け言語での型安全性の考え方

なでしこ3 には静的な型注釈も、コンパイル時の型検査もありません。それでも、本章で見たように次の工夫で安全性を高められます。

1. **入口で型を調べる**: `変数型確認` によるガード節で、想定外の型を関数の入口で失敗結果にする（`安全変換`）
2. **失敗を値にする**: 結果辞書で成功と失敗を返し、呼び出し側に失敗の可能性を意識させる（`成功結果` / `失敗結果`）
3. **例外と使い分ける**: 続行できない失敗は `エラー発生` で止め、`エラー監視` で捕まえる（`厳格変換`）
4. **緩い比較を知る**: `=` や `ASSERT等` は型を区別しないことを学習用テストで確かめ、必要な箇所では型まで比較する（`検証`・`空` の落とし穴）
5. **テストで型を守る**: 型も比較するテスト補助で、戻り値の型の取り違えを検出する

静的型付けの言語が「コンパイラ」に任せる検査を、動的型付けの言語では「実行時のガード」と「テスト」が引き受けます。TDD で小さく確かめながら進めることは、動的型付けの言語でこそ大きな効果を発揮します。

## 12.10 各言語のエラーハンドリング比較

| 概念 | なでしこ3 | Python | Prolog |
|------|-----------|--------|--------|
| 欠損値の表現 | `空`（実体は空文字列） | `None` + `Optional` | `nil` アトム |
| 成功/失敗 | 結果辞書 `{"成功": はい, "値": …}` | 例外 / 戻り値 | `ok(V)` / `error(Msg)` |
| 例外 | `エラー発生` / `エラー監視` | `raise` / `try` | `throw/1` / `catch/3` |
| 型の検査 | `変数型確認`（実行時） | 型ヒント + 実行時 | 型検査述語 + 単一化 |
| 比較の厳密さ | `=`・`ASSERT等` は型を区別しない | `==` は型を区別する | `==` は項として比較 |

### なでしこ3 の日本語 + 動的型付けスタイル

なでしこ3 は、日本語の語順と助詞で引数を渡す、動的型付けのプログラミング言語です。クラス構文を持たないため、第 3 部では辞書と関数を組み合わせてポリモーフィズムや値オブジェクトを表現し、第 4 部では関数を値として渡す高階関数、「〜して〜して」の連鎖によるパイプライン、辞書による結果の表現で FizzBuzz を組み立て直しました。

その過程では、識別子に助詞や「して」を含められない、`ASSERT等` や `=` が型を区別しない、配列が参照型である、といった言語の性質に何度も出会いました。そのたびに学習用テストで振る舞いを確かめ、テスト補助で型まで比較し、`配列複製` や `変数型確認` で安全側に倒す——TDD のサイクルが、言語の癖を「知らないうちに踏む罠」から「テストで守られた前提」に変えてくれました。

プログラムを日本語の文として読めることは、テストを仕様として読めることでもあります。`「元の配列は変わらない」と(元を「,」で配列結合)と「1,2」で検証` は、そのまま仕様書の一文です。FizzBuzz という小さな題材を通じて、TDD の基本サイクルから、辞書と関数による設計、そして関数型のデータ処理と安全なエラー表現まで、**変更を楽に安全にできて役に立つ** ソフトウェアを作るための規律を、日本語で一貫して体験しました。
