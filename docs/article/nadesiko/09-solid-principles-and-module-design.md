# 第 9 章: SOLID 原則とモジュール設計

## 9.1 はじめに

前章までに、辞書と関数でポリモーフィズムと 3 つのデザインパターンを実現しました。この章では **SOLID 原則** の観点からコードを検証し、ファイル単位の **モジュール設計** と依存の向きを整理します。最後に、第 3 章で作ったエントリポイント `src/main.nako3` を第 3 部の部品で書き直し、受け入れテストで振る舞いを確かめます。

なでしこ3 には `module` や `package` のような宣言も、`private` のような公開範囲の指定もありません。モジュールの単位は **ファイル** で、`!「./…」を取り込む` で他のファイルを読み込みます。この章では、この素朴な仕組みでどこまで責務と依存を整理できるかを見ていきます。

## 9.2 ファイル単位の責務分割（SRP）

> クラスが変更される理由は 1 つだけであるべきだ

なでしこ3 ではクラスの代わりに **ファイル** を責務の単位にします。第 3 部終了時点の `src/` は次の通りです。

| ファイル | 主な関数 | 責務 | 変更理由 |
|----------|----------|------|----------|
| `fizzbuzz.nako3` | `FizzBuzz変換` | 基本の FizzBuzz 変換 | FizzBuzz のルールが変わるとき |
| `type.nako3` | `タイプ生成`, `タイプ変換` | タイプごとの変換ルールと生成 | タイプが増減・変更されるとき |
| `value.nako3` | `FizzBuzz値作成`, `数値取得`, `文字列取得`, `FizzBuzz値等価` | 値オブジェクト | 値の表現が変わるとき |
| `list.nako3` | `FizzBuzzリスト作成`, `件数取得`, `文字列一覧取得` | ファーストクラスコレクション | 一覧の操作が変わるとき |
| `command.nako3` | `値コマンド作成`, `リストコマンド作成`, `コマンド実行` | 操作の実行 | 操作の起動方法が変わるとき |
| `main.nako3` | （なし） | 1 から 100 までを表示する | 表示の仕方が変わるとき |

各ファイルの 1 行目のコメントに、そのファイルの責務を 1 文で書いています。1 文で書けないなら、責務が混ざっているサインです。テストもファイルごとに `test/type_test.nako3`・`test/value_test.nako3`・`test/command_test.nako3` と分け、`make test` がそれぞれを別の `gonako run` で実行します。

## 9.3 取り込みと依存の向き

### !「./…」を取り込む

各ファイルは、先頭の `!「./…」を取り込む` で自分が使うファイルだけを読み込みます。

```nako3
# 値オブジェクト（数値と変換結果の組）
!「./type.nako3」を取り込む
```

パスは **取り込む側のファイルの位置** からの相対パスです。`src/value.nako3` からは `./type.nako3`、`test/value_test.nako3` からは `../src/list.nako3` と書きます。どこから `gonako run` しても、同じ書き方で読み込めます。

取り込みは連鎖します。`test/value_test.nako3` は `list.nako3` しか取り込んでいませんが、`list.nako3` が `value.nako3` を、`value.nako3` が `type.nako3` を取り込んでいるので、テストの中で `タイプ生成` も `FizzBuzz値作成` も使えます。

### 依存図

```plantuml
@startuml
title なでしこ3 版 FizzBuzz のファイル依存関係

package "src" {
    [main.nako3] as main
    [command.nako3] as command
    [list.nako3] as list
    [value.nako3] as value
    [type.nako3] as type
    [fizzbuzz.nako3] as fizzbuzz
}

package "test" {
    [type_test.nako3] as type_test
    [value_test.nako3] as value_test
    [command_test.nako3] as command_test
}

package "doctest" {
    [fizzbuzz.txt] as doctest
}

main --> list
command --> list
list --> value
value --> type
type --> fizzbuzz

type_test --> type
value_test --> list
command_test --> command
doctest --> list
@enduml
```

- `fizzbuzz.nako3` は何も取り込みません（最も安定）
- `type.nako3` → `fizzbuzz.nako3` → … と、依存は **一方向** に流れ、循環がありません
- `main.nako3` と `command.nako3` はどちらも `list.nako3` を取り込むだけで、互いに依存しません
- 変わりやすい表示（`main`）や操作（`command`）が、変わりにくい変換ルール（`type`・`fizzbuzz`）に依存する向きになっています

### 名前空間: ファイル名__関数名

取り込んだ関数は、内部では **`ファイル名__関数名`** という名前で登録されます。これまでのエラーメッセージにも、その名前が現れていました。

```
[文法エラー]src/type.nako3(4行目): 関数『type__数字』の定義で以下のエラーがありました。
[文法エラー]src/command.nako3(4行目): 関数『command__値コマンド作成』の定義で以下のエラーがありました。
[文法エラー]test/value_test.nako3(5行目): 未解決の単語があります: [単語『value_test__通常』で,数値3から]
```

普段は `タイプ変換` のように短い名前で呼べますが、修飾した名前でも呼び出せます。

```nako3
!「./src/type.nako3」を取り込む
T = 1からタイプ生成
(Tで3をtype__タイプ変換)を表示
(Tで5をタイプ変換)を表示
```

```bash
$ gonako run ns.nako3
Fizz
Buzz
```

ファイル名が名前空間の役割を果たすので、ファイル名はそのままモジュール名だと考えて付けます。ただし、なでしこ3 には関数を非公開にする仕組みはありません。取り込んだファイルの関数はすべて呼び出せるので、「辞書のキーを直接触らず関数を使う」といった **カプセル化は約束で守る** ことになります。

## 9.4 開放閉鎖原則（OCP）

> ソフトウェアの実体は拡張に対して開いていて、修正に対して閉じているべきだ

新しいタイプを追加するとき、どこが変わるかを実際に試して確かめます（ここでの変更は検証用の作業コピーで行い、`apps/nadesiko` には反映しません）。タイプ 4 として「5 の倍数のときだけ Buzz」の `Buzz限定` を追加します。

```diff
@@ -10,6 +10,11 @@
     Nを文字列変換して戻す
 ここまで
 
+●(Nを)Buzz限定変換
+    もし、N % 5 = 0ならば,「Buzz」を戻す
+    Nを文字列変換して戻す
+ここまで
+
 ●(番号から)タイプ生成
     もし、番号 = 1ならば
         {"名前": "通常", "変換": {関数}FizzBuzz変換}を戻す
@@ -17,6 +22,8 @@
         {"名前": "数字限定", "変換": {関数}数字限定変換}を戻す
     違えば、もし、番号 = 3ならば
         {"名前": "FizzBuzz限定", "変換": {関数}FizzBuzz限定変換}を戻す
+    違えば、もし、番号 = 4ならば
+        {"名前": "Buzz限定", "変換": {関数}Buzz限定変換}を戻す
     ここまで
     「該当するタイプは存在しません: {番号}」のエラー発生
 ここまで
```

変更は `type.nako3` の中だけで、次の 2 点です。

1. 変換関数 `Buzz限定変換` を **追加** する
2. ファクトリ `タイプ生成` に分岐を 1 つ **追加** する

`タイプ変換`・`value.nako3`・`list.nako3`・`command.nako3` は一切変更していません。新しいタイプのテストを書くと、値オブジェクトもリストコマンドもそのまま使えます。

```nako3
!「./helper.nako3」を取り込む
!「../src/command.nako3」を取り込む

Buzz = 4からタイプ生成
「タイプ4は5をBuzzに変換する」と(Buzzで5をタイプ変換)と「Buzz」で検証
「タイプ4は3を数字のまま返す」と(Buzzで3をタイプ変換)と「3」で検証
結果 = (Buzzでリストコマンド作成)で5をコマンド実行
「タイプ4のリストコマンドも使える」と(結果[4]の文字列取得)と「Buzz」で検証
テスト結果報告
```

```bash
$ gonako run test/type4_test.nako3
  ok: タイプ4は5をBuzzに変換する
  ok: タイプ4は3を数字のまま返す
  ok: タイプ4のリストコマンドも使える
  3件成功、0件失敗
```

ところが `make test` を実行すると、既存のテストが 1 件失敗しました。

```bash
$ make test
...
  NG: 未定義のタイプはエラーになる: ASSERT失敗: 『』と『該当するタイプは存在しません: 4』が一致しません。
  8件成功、1件失敗
[実行時エラー]test/type_test.nako3(20行目): 1件のテストが失敗しました
...
テストファイル: 7 件成功、1 件失敗
```

第 7 章のテストは「4 は未定義」という前提で書いていたため、タイプ 4 を定義すると成り立たなくなります。仕様の変更に合わせてテストの番号を `5` に直すと、すべてのテストファイルが通りました（`テストファイル: 8 件成功、0 件失敗`）。変更がテストで即座に検出されるのは、TDD で作ってきた成果です。

関数型言語のパターンマッチや Prolog の節の追加と比べると、ファクトリの `もし` の連鎖に 1 行加える分だけ「修正」が残ります。Python 版の `FizzBuzzType.create()` に 1 行加えるのと同じ程度で、変換ルールそのものは既存の関数に手を入れずに **追加** で拡張できます。

## 9.5 リスコフの置換原則（LSP）とインターフェース分離の原則（ISP）

> サブタイプはそのベースタイプと置換可能でなければならない

型の階層がないなでしこ3 では、「`変換` キーに、数値を受け取って文字列を返す関数を持つ辞書」という **約束** がタイプの基底型に当たります。`タイプ生成` が返す辞書はどれもこの約束を守るので、`FizzBuzz値作成` や `FizzBuzzリスト作成` はどのタイプを渡されても同じように動きます。

> クライアントが使用しないメソッドに依存させてはならない

タイプの約束は `名前` と `変換` の 2 つ、コマンドの約束は `名前` と `実行` の 2 つだけです。それぞれ必要最小限のキーしか要求していません。

## 9.6 依存性逆転の原則（DIP）

> 上位モジュールは下位モジュールに依存してはならない。両方とも抽象に依存すべきだ

`コマンド実行` は、渡された辞書の `実行` を取り出して呼ぶだけです。

```nako3
●(コマンドでNを)コマンド実行
    処理 = コマンド["実行"]
    処理(N)を戻す
ここまで
```

`値コマンド作成` や `リストコマンド作成` の中身には依存していません。依存しているのは「コマンドは `実行` キーに関数を持つ辞書である」という **約束（抽象）** だけです。その証拠に、`command.nako3` に手を入れずに、その場で作ったコマンドも実行できます。

```nako3
!「./src/command.nako3」を取り込む
処理 = 関数(N)
    [N × 2]を戻す
ここまで
倍コマンド = {"名前": "倍コマンド", "実行": 処理}
(倍コマンドで21をコマンド実行)[0]を表示
```

```bash
$ gonako run dip.nako3
42
```

```
コマンド実行 ──→「実行」キーを持つ辞書（約束） ←── 値コマンド / リストコマンド / 倍コマンド
タイプ変換   ──→「変換」キーを持つ辞書（約束） ←── 通常 / 数字限定 / FizzBuzz限定
```

型宣言やインターフェース構文はありませんが、辞書のキー名という約束を介して、上位（コマンドの実行）と下位（個々のコマンド）がどちらも同じ抽象に依存しています。約束が守られているかどうかは、コンパイラではなく **テスト** が確かめます。

## 9.9 各言語のモジュール設計比較

| 概念 | なでしこ3 | Python | Prolog |
|------|-----------|--------|--------|
| モジュール単位 | ファイル | モジュール（ファイル）/ パッケージ | `module/2`（ファイル） |
| 依存宣言 | `!「./…」を取り込む` | `import` | `use_module/1` |
| 名前空間 | `ファイル名__関数名` | モジュール名 | モジュール名 |
| 公開制御 | なし（約束で守る） | `_` 接頭辞（慣習） | エクスポートリスト |
| 抽象 | 辞書のキーの約束 | `abc.ABC` | 述語の契約 |

### Before / After

**Before**（第 2 部終了時）:

```
src/
├── fizzbuzz.nako3   (FizzBuzz変換, FizzBuzz配列作成)
└── main.nako3       (FizzBuzz配列作成 の結果を表示)
```

**After**（第 3 部終了時）:

```
src/
├── fizzbuzz.nako3   (基本の変換)
├── type.nako3       (タイプの辞書と生成)
├── value.nako3      (値オブジェクト)
├── list.nako3       (ファーストクラスコレクション)
├── command.nako3    (コマンド)
└── main.nako3       (エントリポイント)
```

クラスも `private` もインターフェースもありませんが、「関数を値として辞書に入れる」「辞書のキーを触るのはそのファイルの関数だけにする」「ファイルを責務の単位にして一方向に取り込む」という 3 つの約束で、オブジェクト指向設計の考え方をなでしこ3 に持ち込めました。約束が破られていないことは、`make check` のテストが保証します。

次の第 4 部では、関数型プログラミングの観点から FizzBuzz を再構成し、高階関数、不変データ、パイプライン、エラーハンドリングを学びます。
