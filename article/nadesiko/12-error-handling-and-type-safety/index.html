    第 12 章: エラーハンドリングと型安全性¶

    12.1 はじめに¶

    第 4 部の締めくくりとして、エラーを 値として返す 結果辞書（Result 相当）、空 による欠損の表現（Option 相当）、そして動的型付け言語であるなでしこ3 で実行時の型チェックによって安全性を担保する方法を学びます。

    なでしこ3 には、「…」のエラー発生 でエラーを起こし、エラー監視 … エラーならば … ここまで で捕まえる例外の仕組みがあります。第 2 章のテスト補助 検証 や、第 3 部のタイプの生成（存在しない番号でエラーを発生させる）ですでに使ってきました。本章では、それとは別に、成功と失敗を 辞書の値 として返すやり方を TDD で実装し、両者を使い分けます。

    この章で学ぶこと¶

    • 成功と失敗を辞書で表す 成功結果 / 失敗結果（Result 相当）
    • 変数型確認 による動的な型チェックと、0 以下を拒否する 安全変換
    • 失敗時にエラーを発生させる 厳格変換 と、エラー監視 による捕捉
    • 空 を受け付ける 空許容変換（Option 相当）と、その落とし穴
    • ASSERT等 が緩い比較であることの再確認と、テスト補助で型を比べる意味
    • 動的型付け言語での型安全性の考え方と、第 4 部・シリーズ全体の振り返り

    12.2 例外と「エラーを値として返す」アプローチ¶

    例外は、エラーが起きた場所から エラー監視 まで処理を一気に飛ばします。通常の流れから外れた失敗を扱うには便利ですが、呼び出し側が エラー監視 を書き忘れると、プログラムはそこで止まってしまいます。

    これに対して、成功と失敗を 値 として返すのが Result のアプローチです。Kotlin や Rust には Result 型がありますが、なでしこ3 にはクラス構文も独自の型を定義する仕組みもありません。そこで、第 3 部の値オブジェクトと同じく 辞書 を使います。

    成功: {"成功": はい, "値": 変換結果}
失敗: {"成功": いいえ, "エラー": メッセージ}

    戻り値の "成功" を見れば、呼び出し側は必ず失敗の可能性に気付けます。

    TODO リスト:

    • 正の数は成功の結果辞書を返す（成功結果・安全変換）
    • 0 以下は失敗の結果辞書を返す（失敗結果）
    • 数値以外は失敗の結果辞書を返す（動的な型チェック）
    • 失敗時にエラーを発生させる 厳格変換
    • 空 を受け付ける 空許容変換

    実装は src/error.nako3 に置き、テストは test/error_test.nako3 に書きます。

    12.3 成功結果と安全変換¶

    12.9 動的型付け言語での型安全性の考え方¶

    なでしこ3 には静的な型注釈も、コンパイル時の型検査もありません。それでも、本章で見たように次の工夫で安全性を高められます。

    1. 入口で型を調べる: 変数型確認 によるガード節で、想定外の型を関数の入口で失敗結果にする（安全変換）
    2. 失敗を値にする: 結果辞書で成功と失敗を返し、呼び出し側に失敗の可能性を意識させる（成功結果 / 失敗結果）
    3. 例外と使い分ける: 続行できない失敗は エラー発生 で止め、エラー監視 で捕まえる（厳格変換）
    4. 緩い比較を知る: = や ASSERT等 は型を区別しないことを学習用テストで確かめ、必要な箇所では型まで比較する（検証・空 の落とし穴）
    5. テストで型を守る: 型も比較するテスト補助で、戻り値の型の取り違えを検出する

    静的型付けの言語が「コンパイラ」に任せる検査を、動的型付けの言語では「実行時のガード」と「テスト」が引き受けます。TDD で小さく確かめながら進めることは、動的型付けの言語でこそ大きな効果を発揮します。

    なでしこ3 の日本語 + 動的型付けスタイル¶

    なでしこ3 は、日本語の語順と助詞で引数を渡す、動的型付けのプログラミング言語です。クラス構文を持たないため、第 3 部では辞書と関数を組み合わせてポリモーフィズムや値オブジェクトを表現し、第 4 部では関数を値として渡す高階関数、「〜して〜して」の連鎖によるパイプライン、辞書による結果の表現で FizzBuzz を組み立て直しました。

    その過程では、識別子に助詞や「して」を含められない、ASSERT等 や = が型を区別しない、配列が参照型である、といった言語の性質に何度も出会いました。そのたびに学習用テストで振る舞いを確かめ、テスト補助で型まで比較し、配列複製 や 変数型確認 で安全側に倒す——TDD のサイクルが、言語の癖を「知らないうちに踏む罠」から「テストで守られた前提」に変えてくれました。

    プログラムを日本語の文として読めることは、テストを仕様として読めることでもあります。「元の配列は変わらない」と(元を「,」で配列結合)と「1,2」で検証 は、そのまま仕様書の一文です。FizzBuzz という小さな題材を通じて、TDD の基本サイクルから、辞書と関数による設計、そして関数型のデータ処理と安全なエラー表現まで、変更を楽に安全にできて役に立つ ソフトウェアを作るための規律を、日本語で一貫して体験しました。
