    コラム: なでしこ3 を Python 風に書く¶

    第 9 章では、なでしこ3 を基準に置き、他の 17 言語をなでしこ3 に近づけました。 本章は向きを逆にします。なでしこ3 を Python に近づけて書き、FizzBuzz とボウリングゲームを Python と TDD で並べながら育てます。

    下敷きにしたのは、天清会の note 記事 「メモ：Python風に書ける「なでしこ3」の資料を整備、notebookLMに追加しました」 と、その記事で配布されている「なでしこ3をPython風に書くマニュアル」です。 このマニュアルは、なでしこ3 の公式文法にある 行末のコロンとインデントでブロックを表す書き方（Python 風インラインインデント構文）に記法を統一し、 Python へ移行したときに制御構造の形が変わらないことを狙っています。

    マニュアルはブラウザ版（wnako v3.7.24）で検証されています。 本章のコードは、本シリーズの処理系である Go 版の gonako v3.8.8 で改めて実行し、テストが通ることを確認しました。 あわせて、公式の JavaScript 版 cnako3 v3.8.7 でも同じテストが通ることを確かめています。 コードは apps/pystyle/nadesiko/ と apps/pystyle/python/ にあります。

    注意: 本章の書き方は、本シリーズのなでしこ3 編の書き方とは異なります。 本編は「ここまで」でブロックを閉じ、助詞で引数を渡す日本語らしい書き方を基本にしています。 どちらが正しいという話ではなく、なでしこ3 が両方を受け入れることを示すのが本章の目的です。

    問い¶

    1. なでしこ3 は、どこまで Python と同じ形で書けるか
    2. TDD のサイクル（Red → Green → Refactor）を両言語で並べたとき、どこで差が出るか
    3. Python 風に書くことで、なでしこ3 の何が得られ、何が失われるか

    Python 風インラインインデント構文の規則¶

    マニュアルが定める規則のうち、本章のコードに関わるものを抜き出します。

    規則 なでしこ3（Python 風） Python
    ブロックの開始 行末に半角の : 行末に :
    ブロックの範囲 半角スペース 4 個の字下げ 字下げ（PEP 8 では 4 個）
    ブロックの終了 字下げを戻す（「ここまで」は使わない） 字下げを戻す
    関数の呼び出し 表示(式)・要素数(リスト) print(式)・len(リスト)
    関数の名前 末尾に「処理」を付ける（加算処理） 規則なし

    テストデータを作る関数¶

    20 投ぶんの配列をテストに直接書くと読みにくいため、配列の後ろに同じ値を N 個つなげる関数を用意します。

    def 同値連結処理(配列: list[int], PINS: int, N: int) -> list[int]:
    結果 = list(配列)
    for 番号 in range(1, N + 1):
        結果.append(PINS)
    return 結果

    変数のF結果 = 配列複製(配列)
    # cnako3 の「繰り返す」は開始が終了より大きいと逆向きに回るため、0 件を先に返す
    もし(N < 1)ならば:
        F結果を戻す
    番号を1からNまで繰り返す:

    ステップ 3: スペア（フレームという単位の導入）¶

    「スペアは次の 1 投を加算する」は、[5, 5, 3] のあとに 0 を 17 投つなげて 16 点を期待します。 合計のままでは 13 点になり、テストが失敗します。 投球を 1 つずつ見るのではなく、フレーム という単位で 10 回繰り返す形に変えます。

    def 得点計算処理(投球列: list[int]) -> int:
    得点 = 0
    位置 = 0
    for _ in range(10):
        if 投球列[位置] + 投球列[位置 + 1] == 10:
            得点 = 得点 + 10 + 投球列[位置 + 2]
        else:
            得点 = 得点 + 投球列[位置] + 投球列[位置 + 1]
        位置 = 位置 + 2
    return 得点

    変数のF得点 = 0
    変数のF位置 = 0
    10回、繰り返す:
        もし(投球列[F位置] + 投球列[F位置 + 1] = 10)ならば:
            F得点 = F得点 + 10 + 投球列[F位置 + 2]
        違えば:
            F得点 = F得点 + 投球列[F位置] + 投球列[F位置 + 1]
        F位置 = F位置 + 2
    F得点を戻す

    ループ変数を使わない回数の繰り返しは、for _ in range(10): が 10回、繰り返す: に対応します。 マニュアルの対照表にもある組み合わせです。 配列の添字は、どちらも 0 から始まり、投球列[位置 + 1] の形もそのまま同じです。

    ステップ 4〜5: ストライクとパーフェクトゲーム¶

    「ストライクは次の 2 投を加算する」（[10, 3, 4] のあとに 0 を 16 投、合計 19 投）を加えると、ステップ 3 のコードでは失敗します。 ここで、両言語の失敗の仕方が分かれます。

    # Python
E   IndexError: list index out of range

    ストライクのフレームも 2 投ずつ進めるため、10 フレーム目で 19 投の配列の外（添字 19）を読みます。 Python は範囲外の添字で例外を投げて止まりますが、なでしこ3 は例外にならず、存在しない要素との足し算が NaN になって計算が続きます （cnako3 でも NaN !== 24 でした）。 今回は期待値との比較で気づけましたが、範囲外の読み取りは処理系が止めてくれない ことを覚えておく必要があります。

    先頭にストライクの分岐を足します。 ストライクのフレームは 1 投で終わるため、位置は 1 だけ進めます。

    def 得点計算処理(投球列: list[int]) -> int:
    得点 = 0

private const val FRAMES_PER_GAME = 10
private const val ALL_PINS = 10

private fun scoreFrames(rolls: List<Int>, remainingFrames: Int): Int =
    when {
        remainingFrames == 0 -> 0
        rolls.isStrike() -> rolls.frameScore(rollsUsed = 1, bonusRolls = 2) + rolls.nextFrames(1, remainingFrames)
        rolls.isSpare() -> rolls.frameScore(rollsUsed = 2, bonusRolls = 1) + rolls.nextFrames(2, remainingFrames)
        else -> rolls.frameScore(rollsUsed = 2, bonusRolls = 0) + rolls.nextFrames(2, remainingFrames)
    }

private fun List<Int>.isStrike(): Boolean = first() == ALL_PINS

private fun List<Int>.isSpare(): Boolean = take(2).sum() == ALL_PINS

private fun List<Int>.frameScore(rollsUsed: Int, bonusRolls: Int): Int = take(rollsUsed + bonusRolls).sum()

private fun List<Int>.nextFrames(rollsUsed: Int, remainingFrames: Int): Int =
    scoreFrames(drop(rollsUsed), remainingFrames - 1)

    状態がリストそのものに入っている: ループ版の 位置 は、「投球列のどこまでを使い終えたか」という状態でした。 Kotlin 版は、使い終えた投球を drop で取り除いたリストを次の呼び出しに渡します。 そのため、どの関数も常に「リストの先頭」だけを見れば済みます。 isStrike が first()、isSpare が take(2) と短く書けるのはこのためです。 添字の計算（位置 + 1・位置 + 2）が、コードから消えています。

    命令名と変数名の衝突¶

    マニュアルは、合計・対象・回数 などを変数名に使うと標準命令や特殊変数と衝突することがあると注意しています。 関数名の末尾に「処理」を付け、ローカル変数に F を付ける規則は、この衝突を避けるためのものです。 本章のコードでも FizzBuzz変換処理・変数のF結果 と、この規則に従っています。

    助詞を含む変数名¶

    マニュアルは、助詞を含む変数名も避けるよう注意しています。 ボウリングのテストを書いている途中で、2 つ目のゲームを 別のゲーム と名付けたところ、文法エラーになりました。

    別のゲーム = ゲーム作成処理

    [文法エラー]test/bowling_oo_test.nako3(11行目): 不完全な文です。単語『bowling_oo_test__別』、演算子『＝』が解決していません。演算子『＝』は『単語『bowling_oo_test__ゲーム』と関数『bowling_oo__ゲーム作成処理』が等しいかどうかの比較』として使われています。

    「の」が助詞として読まれ、別 と ゲーム の 2 語に分かれています。 さらに、行頭の代入のつもりだった = が、ゲーム と ゲーム作成処理 の比較として解釈されています。 代入と比較に同じ = を使うなでしこ3 ならではのエラーです（gonako・cnako3 とも同じメッセージでした）。 Python では 別のゲーム = ゲーム() は普通の代入なので、Python の感覚で名前を付けるとつまずきます。 本章では ゲーム2 に改めました。

    考察: Python への橋渡しとしてのなでしこ3¶

    マニュアルの狙いは、なでしこ3 で学んだ人が Python へ移るとき、制御構造の形を学び直さずに済む ことです。 FizzBuzz とボウリングゲームを TDD で並べてみると、その狙いはおおむね達成されていました。 分岐・反復・関数定義の骨格は 1 行ずつ対応し、違いは単語と語順に収まります。 マニュアルの言葉を借りれば、なでしこ3 のコードは「仕様書とプログラムの距離を縮め」ます。 Python 風に書けば、その距離を保ったまま、プログラムと Python の距離も縮められます。

    一方で、Python 風にすると失われるものもあります。

    • 助詞による引数: 配列結合(リスト,「,」) は、本編の リストを「,」で配列結合 に比べて、どちらが区切り文字かが字面から読み取りにくくなります
    • 文としての読みやすさ: 本編の Nを文字列変換して戻す は日本語の文として読めますが、文字列変換(N)を戻す は関数呼び出しに日本語の語尾が付いた形になります
    • 誤りの検出: 見た目は Python と同じでも、字下げの誤りや範囲外の添字を処理系が検出してくれません
    • 引数の名前: Python のキーワード引数のように呼び出し側で数の意味を示せないため、ボウリングの フレーム得点処理(投球列,F位置,1,2) は定義を見ないと読めません
    • クラス: クラス構文がないため、オブジェクト指向版は辞書と関数で組み立てることになります。ただし、得点の計算を状態のない関数に切り出しておけば、その差は薄い殻の部分に閉じ込められます

    第 9 章は、他の言語がなでしこ3 に近づこうとすると代償があることを示しました。 本章は逆向きにも代償があることを示しています。 どちらに寄せるかは、読み手と目的で決めます。 日本語で考えて仕様を書くことが目的なら本編の書き方、Python へ進む準備が目的なら Python 風の書き方が向いています。 TDD のテストは、どちらの書き方でも同じ日本語の文章で書けるため、書き方を切り替えても仕様として読めます。
