    執筆計画アウトライン¶

    概要¶

    「テスト駆動開発から始めるプログラミング入門」シリーズの執筆計画。Wiki 記事（エピソード 1〜4）の内容を再構成し、16 言語環境で統一的な章構成の記事として執筆する。

    対象言語¶

    ops/nix/environments/ に定義された 16 言語環境：

    環境名 言語 エピソード数 備考
    java Java 3 OOP 代表
    node JavaScript / TypeScript 3 + 3 2 言語を 1 環境で
    python Python 3 マルチパラダイム
    ruby Ruby 4 エピソード 4 はパフォーマンス
    php PHP 3 Web 特化
    go Go 3 シンプル志向
    rust Rust 3 所有権・メモリ安全性
    dotnet C# / F# 3 + 4 2 言語を 1 環境で
    clojure Clojure 4 LISP + 関数型
    scala Scala 4 OOP + FP ハイブリッド
    elixir Elixir 4 Erlang VM + 関数型
    haskell Haskell 4 純粋関数型
    flix Flix 4 JVM + 関数型・代数的効果
    kotlin Kotlin 4 JVM + OOP・FP ハイブリッド
    prolog Prolog 4 論理型・宣言的（SWI-Prolog）
    nadesiko なでしこ3 4 日本語プログラミング言語（Go 版 gonako）

    章構成¶

    Wiki 記事のエピソード 1〜4 を 12 章に再構成する。

    第 1 部: TDD の基本サイクル（エピソード 1 相当）¶

    Wiki エピソード 1 の内容を 3 章に分割。FizzBuzz 問題を題材にした TDD サイクルの体験。

    章 テーマ Wiki 参照元 内容
    1 TODO リストと最初のテスト エピソード 1 前半 仕様理解、TODO リスト作成、テスティングフレームワーク導入、テストファースト
    2 仮実装と三角測量 エピソード 1 中盤 仮実装（ハードコーディング）、三角測量による一般化
    3 明白な実装とリファクタリング エピソード 1 後半 明白な実装、学習用テスト、「動作するきれいなコード」

    第 2 部: 開発環境と自動化（エピソード 2 相当）¶

    なでしこ3 追加執筆計画¶

    なでしこ3 は日本語で記述するプログラミング言語で、「〜を〜する」という日本語の語順（助詞による引数指定）でプログラムを書く点が特色。これまでの 15 言語がすべて英語のキーワードに基づくのに対し、なでしこ3 は「日本語でテストを書き、日本語で設計を語る」体験を提供する。実行系には Go 実装の nadesiko3go（コマンド名 gonako、MIT ライセンス）を採用する。公式実装は TypeScript 版（cnako3）であり、Go 版はその互換バックエンドとして位置づけられている（docs/differences.md）。単一バイナリで動作し、lint・format・doctest のサブコマンドを備える点を採用理由とする。

    関数定義（●(Nを)FizzBuzz変換）・条件分岐（もし…ならば）・繰り返し（Iを1から100まで繰り返す）・配列と辞書・無名関数（関数(x)…ここまで）・配列マップ/配列フィルタ・エラー監視/エラー発生・ファイルの取り込み（!「./lib.nako3」を取り込む）が Go 版で動作することを確認済み。クラス構文は Go 版の lexer/parser に見当たらないため、第 3 部の「オブジェクト指向設計」は 辞書（ハッシュ）によるデータ表現・関数を値として格納した辞書によるディスパッチ・ファイル取り込みによるモジュール分割 へ読み替える（Prolog の複数節ディスパッチと同様の読み替え方針）。第 4 部は無名関数と配列の高階命令で全 3 章を執筆できるため、全 4 部（12 章）構成とする。

    テストは Go 版に組み込まれた表明命令 【A】と【B】がASSERT等（不一致時に ASSERT失敗 の実行時エラーを出し終了コード 1）を用いる。Go 版には TypeScript 版の テスト実行・cnako3 -t に相当するテストランナーが無いため、test/*.nako3 を 1 ファイルずつ gonako run で実行し終了コードで合否を判定する test runner（Makefile）を自作する。記事中のコード例は gonako doctest（{{{#nako3 … ### 表示結果: … }}} の出力照合）で検証する。

    日本語実装比較コラム 執筆計画¶

    なでしこ3 の実装（apps/nadesiko/）を、他の 17 言語（Java・JavaScript・TypeScript・Python・Ruby・PHP・Go・Rust・C#・F#・Clojure・Scala・Elixir・Haskell・Flix・Kotlin・Prolog）で 識別子・テスト名・エラーメッセージを日本語にして 書き直し、「日本語でプログラムを書く」ことが各言語でどこまで自然にできるかを比較するコラムを、多言語統合解説の第 9 章として追加する。

    第 8 章のコラム が比喩で言語の性格を描いたのに対し、本コラムは実コードで「日本語化の許容度」を測る。なでしこ3 はトータルスコアでは最下位（6.1）だが、日本語で書くという一点では他言語が追いつけない基準点であり、その差を具体的なコードで示すことが本コラムの狙いである。

    問い¶

    1. 日本語の識別子（関数・変数・型・モジュール名）は各言語で書けるか。書けない場合、どの規則が阻むのか
    2. テスト名を日本語の文章にできるか（なでしこ3 の 「3を渡したらFizzを返す」と…で検証 に相当する表現）
    3. なでしこ3 の「助詞による引数」と「日本語の語順（SOV）」を、拡張メソッド・中置記法・パイプライン・演算子定義でどこまで再現できるか
    4. 日本語化したときに lint・formatter・テストランナー・ファイルシステムはどう反応するか

    B. タイプ生成 src/type.nako3（タイプ生成・タイプ変換） 型・クラス・列挙子・コンストラクタ名の大文字制約、ディスパッチの表現

    D. 安全変換 src/error.nako3（安全変換・成功結果・失敗結果） 日本語のエラーメッセージ、Result 型・例外の型名を日本語にできるか

    評価軸（日本語化スコア）¶

    各軸 0〜3 点、満点 15 点。第 7 章 と同様に「優劣ではなくカバー範囲」を測る注記を付ける。

    軸 3 点 0 点
    関数・変数名 制約なく日本語で書ける 日本語を書けない
    型・モジュール名 型・列挙子・モジュール・ファイル名すべて日本語可 すべて ASCII 必須
    テスト名 文章（空白・記号込み）で書ける ASCII の関数名のみ
    語順の再現 3を FizzBuzz変換 に近い SOV 順で書ける 前置の関数呼び出しのみ
    ツール許容 lint・formatter・テストランナーが警告なく通る 警告抑止や設定変更が必須

    なでしこ3 は全軸 3 点（15 点）の基準点とし、残り 17 言語を実測で採点する。

    事前調査で確認済みの制約¶

    本計画作成時点で、手元の処理系で以下を実行確認した（他の言語は実装時に検証する）。

    言語 確認した挙動 確認環境
    Python 関数・クラス名とも日本語可。識別子は NFKC 正規化されるため半角 ｶ と全角 カ が同一視される Python 3
    JavaScript 関数・クラス・プロパティ名とも日本語可 Node.js 22
    Ruby メソッド・ローカル変数は日本語可。Integer を開いて 15.FizzBuzz変換 と後置で書ける。一方 class タイプ は class/module name must be CONSTANT でエラー。全角大文字で始めた class Ｔタイプ は通る Ruby 3.3
    PHP 関数・クラス名とも日本語可 PHP 8
    Go 日本語の関数名・パッケージ名は書けるが、大文字始まりでないため 非公開扱い になり他パッケージから 型.日本語関数 を呼べない（FizzBuzz変換 のように ASCII 大文字で始めれば公開される）。import パスに日本語は使えない（malformed import path）。func Test3を渡したらFizzを返す はテストとして実行される Go 1.24
    Rust 日本語の関数・構造体・列挙子は警告なしでコンパイルできる。mod 変換; のようにファイルからモジュールを読むと E0754（non-ascii なモジュール名のファイル読み込み不可）でエラー rustc 1.94
    Java クラス・メソッド名とも日本語可。ただしファイル名 タイプ.java はロケールが UTF-8 でないと読めない OpenJDK 21

    実装時に検証する仮説¶

    言語 仮説（要検証）
    TypeScript 型エイリアス・列挙子も日本語可。ESLint の命名規則（naming-convention）の設定次第で警告
    C# 識別子は日本語可。xUnit の DisplayName で文章のテスト名
    F# 二重バッククォートで囲んだ関数名（3 を渡したら Fizz を返す）で空白込みのテスト名。判別共用体のケース名は大文字始まりが必要か（FS0053）を確認。\|> で SOV 順に近づく
    Kotlin バッククォートの関数名で文章のテスト名。拡張関数 3.FizzBuzz変換() と infix で語順を寄せる
    Scala 識別子は日本語可。パターンマッチで日本語の識別子が変数束縛と定数参照のどちらに解釈されるか。拡張メソッドと中置記法で 3 を 変換 に近づけられるか
    Clojure シンボル・キーワードとも日本語可。-> スレッディングで SOV 順
    Elixir 変数・関数・アトムは日本語可。モジュール名（エイリアス）は ASCII 必須と予想。\|> で SOV 順
    Haskell 日本語は小文字扱いのため関数・変数は可、型・データ構築子は大文字始まりが必要で不可と予想。バッククォート中置 3 `を` 変換
    Flix 識別子の Unicode 対応状況自体を確認する
    Prolog 日本語で始まるトークンはアトム扱いのため述語名は可、変数は大文字か _ 始まりが必要。op/3 で を などを中置演算子として定義し、なでしこ3 に最も近い語順を狙う

    記事構成案¶

    1. はじめに -- なでしこ3 を基準点に置く理由
    2. 題材となるなでしこ3 のコード（題材 A〜D）
    3. 関数と変数を日本語にする -- ほぼ全言語で書けることの確認
    4. 型とモジュールを日本語にする -- 大文字規則（Ruby・Go・Haskell・Elixir・Prolog）とファイル名（Rust・Java）の壁
    5. テスト名を日本語の文章にする -- 文字列・バッククォート・DisplayName・関数名の 4 方式
    6. 語順を日本語に寄せる -- 後置メソッド、中置、パイプライン、演算子定義
    7. 日本語化スコア一覧とレーダーチャート
    8. 考察 -- 「書ける」と「書くべき」の区別（チーム・ツール・検索性）、なでしこ3 の価値

    進め方¶

    1. 題材 A は TDD で進める。なでしこ3 のテストケース（3を渡したらFizzを返す など 7 件）をそのまま日本語のテスト名として各言語へ移し、Red → Green を確認してから日本語化の工夫（語順・後置呼び出し）をリファクタリングとして加える。
    2. 言語仕様で書けない箇所は回避策（ASCII 接頭辞、全角大文字、#[path] 属性など）を試し、回避策の有無と代償をスコアの根拠として記録する。
    3. 事実確認を徹底し、仮説表の項目は実行結果が出るまで記事に断定で書かない。確認した処理系のバージョンを記事に明記する。

    既知の制約とリスク¶

    制約・リスク 影響 対策
    17 言語すべてのツールチェーンが必要 検証環境の準備に時間がかかる 既存の Nix 環境（nix develop .#{lang}）を再利用し、新規の依存は追加しない

    ロケール・ファイル名の文字コード依存（Java など） CI で再現しない CI とローカルで LANG=C.UTF-8 を明示する
    「日本語で書けるべき」という主張に受け取られる 記事の意図が誤解される 第 7・8 章と同様に、スコアは許容度の比較であり推奨ではないと注記する

    なでしこ3 Python 風記法コラム 執筆計画¶

    天清会の note 記事「メモ：Python風に書ける「なでしこ3」の資料を整備、notebookLMに追加しました」と、同記事で配布されている「なでしこ3をPython風に書くマニュアル」を参考に、なでしこ3 を Python 風インラインインデント構文（行末のコロンと字下げ、「ここまで」を使わない）で書き、Python の FizzBuzz とボウリングゲームを TDD で並べて育てるコラムを、多言語統合解説の第 10 章として追加する。

    第 9 章 が他言語をなでしこ3 に近づけたのに対し、本コラムは逆向きに、なでしこ3 を Python に近づけたときの対応と代償を示す。
